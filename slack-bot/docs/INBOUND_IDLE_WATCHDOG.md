# 무수신(connected-but-no-inbound) 감지·자가복구 — 사양 및 운영 절차

- 대상: `slack-bot` (Slack Socket Mode 봇)
- 도입 근거: giip #5141 — "소켓은 연결됐는데 이벤트가 한 건도 안 오는" 상태를 감지·자가복구하지 못함
- 코드: [`slack-bot/inbound-idle-watchdog.js`](../inbound-idle-watchdog.js), [`slack-bot/inbound-probe.js`](../inbound-probe.js)

## 1. 문제

기존 self-heal 워치독은 두 가지만 감지했다.

| 감지 대상 | 구현 | 비고 |
|---|---|---|
| 재연결 실패 | `armReconnectWatch` — `disconnecting`/`disconnected`/`reconnecting` 후 `RECONNECT_GRACE_MS`(120초) 안에 복구 안 되면 `dieAndRestart()` | 소켓이 **떨어진** 경우 |
| ack 연속 실패 | `safeAck` — `ACK_FAIL_LIMIT`(6)회 연속 ack 실패 | 소켓이 **보내지를** 못 하는 경우 |

**"소켓은 `connected` 인데 인바운드 프레임이 한 건도 오지 않는"** 상태는 위 두 타이머를 전혀 울리지
않는다. pm2 는 프로세스 생존만 보고 정상으로 취급해 재시작하지 않고, 봇은 무한 무응답이 된다.
2026-11-13 실측: 13:07 재시작 직후 새 연결이 `Socket Mode 接続完了` 로 떴지만 13:08 에 사용자가 보낸
`@lowyclaude !help` 에 대한 수신 프레임이 0건이었다(같은 요청은 다음 재시작에서 정상 처리).

## 2. 감지 동작

### 2.1 상수 (`slack-bot/index.js`)

| 상수 | 기본값 | 의미 |
|---|---|---|
| `INBOUND_IDLE_MS` | `15 * 60 * 1000` (15분) | 소켓이 살아 있는데 인바운드 프레임이 안 오는 상태로 간주하는 임계 |
| `INBOUND_PROBE_INTERVAL_MS` | `5 * 60 * 1000` (5분) | 임계 초과 후 능동 점검(트래픽 대조) 주기 |

### 2.2 판정 흐름

1. `ws_message` 가 한 건이라도 오면 마지막 수신 시각을 갱신한다(연결 직후 `hello` 프레임도 포함).
2. `connected`/`authenticated` 이벤트에서 무수신 시계를 초기화한다(재연결 직후 다시 유예).
3. 주기 점검에서 `now - 마지막 수신 >= INBOUND_IDLE_MS` 이면 **능동 점검**을 돌린다.
4. 능동 점검(`slack-bot/inbound-probe.js`)은 두 가지를 확인한다.
   - `auth.test` — Web API 경로가 살아 있는지.
   - `conversations.history` — 대조 대상 채널에 **"우리가 반드시 이벤트를 받았어야 하는"** 메시지가
     마지막 수신 이후 도착했는지.
     대조 창은 **슬랙 서버 ts 영역**에서만 비교한다(§3-9).
5. 판정에 따라 분기한다.

| 판정 | 조건 | 동작 |
|---|---|---|
| **의심(suspect)** | `auth.test` 가 API 오류로 실패(토큰 무효 등) | 자가 재시작 |
| **의심(suspect)** | API 는 정상 + "받았어야 할 트래픽" 존재 + 우리 프레임 0건 | 자가 재시작 |
| 유휴(idle) | API 정상 + 트래픽 없음 | **죽이지 않는다** (진짜 무트래픽 시간대) |
| 판정 불가 | API 도달 실패 / `conversations.history` 권한 없음 / 대조 채널 0건 | **죽이지 않는다** (오탐 방지) |

6. 자가 재시작 = `dieAndRestart(why)` → `process.exit(1)` → pm2 가 재시작한다
   (pm2 `autorestart: true` 전제).

### 2.3 로그

| 로그 | 의미 |
|---|---|
| `[Bot] 무수신 감지: no inbound frames for Ns (socket silently stuck) — <상세>` | 자가 재시작 발동 |
| `[Bot] self-heal: no inbound frames for Ns (socket silently stuck) — <상세>. Exiting so pm2 restarts.` | 기존 자가치유 로그(종료 직전) |
| `[Bot] 무수신 점검: Ns 동안 인바운드 프레임 없음 — <상세> (자가 재시작 안 함)` | 진짜 유휴 또는 판정 불가 |

## 3. 오탐 방지 조건 (필수 사양)

자가 재시작은 **작업 중인 태스크를 끊을 수 있으므로** 아래 조건을 모두 만족할 때만 수행한다.

| # | 조건 | 값/기준 | 근거 |
|---|---|---|---|
| 1 | 무수신 임계 | `INBOUND_IDLE_MS` **하한 15분** | 그보다 짧으면 정상적인 무활동 시간대(야간 등)에 자가 재시작이 발생한다 |
| 2 | 점검 주기 | `INBOUND_PROBE_INTERVAL_MS` **하한 1분, 상한 `INBOUND_IDLE_MS`/3** | 너무 짧으면 Slack Web API 호출 폭주, 너무 길면 감지 지연 |
| 3 | 트래픽 판정 기준 | 아래 3가지만 트래픽으로 계상한다. ① **DM(im/mpim) 메시지** ② **봇을 멘션한 채널 메시지** ③ **앱이 채널 메시지 이벤트를 우리에게 준 경우**(실제로 그런 이벤트를 받은 적이 있을 때)에 그 채널의 사람 메시지 전체 | 채널의 일반 잡담은 우리에게 이벤트로 오지 않는다. 이것까지 세면 "봇이 말을 걸지 않은 대화"만으로 재시작하는 오탐이 생긴다. ③ 은 **받은 적이 있을 때만** 켠다(앱 구독 범위를 추정하지 않는다) |
| 4 | 자기 송신 제외 | `bot_id`/`user` 가 우리 것인 메시지는 제외 | 봇이 스스로 올린 메시지를 놓친 것으로 오인해 재시작하면 안 된다 |
| 5 | 과거 메시지 제외 | 마지막으로 **받은 이벤트의 ts(서버 시계)** 이전 메시지는 제외 | 오래된 트래픽으로 오탐하지 않는다 |
| 6 | 판정 불가 시 생존 | API 도달 실패·권한 부족·대조 채널 0건이면 **죽이지 않는다** | 판단 근거가 없는 상태에서 프로세스를 죽이면 그 자체가 장애다 |
| 7 | 단절 상태 위임 | 소켓이 `disconnected` 면 점검하지 않는다 | 기존 재연결 워치독(`RECONNECT_GRACE_MS`)이 담당. 중복 판정·중복 종료 방지 |
| 8 | 트래픽 기준 시간 | 마지막 **인바운드 프레임** 기준 | 수신이 마지막이 아니라 "이벤트가 마지막"이 아니다 — 어느 프레임이든 오면 시계가 초기화된다 |
| 9 | **시계 영역 분리** | 트래픽 대조 창은 **슬랙 서버 ts** 로만 비교한다(로컬 시계로 만든 창과 섞지 않는다) | 슬랙 ts 는 서버 시계다. 로컬 시계가 서버보다 느리면 **우리가 이미 받은 메시지**가 "놓친 메시지"로 오인되어, 유휴할 때마다 자가 재시작하는 구조적 오탐이 된다. 기준점은 "마지막으로 받은 이벤트의 ts"(서버 시계)로 잡고, 그 기준점이 아직 없을 때(이벤트를 한 번도 못 받은 경우)에만 로컬 시계로 대체 창을 쓰되 오탐 폭을 **5초**로 제한한다 |

## 4. 필요한 Slack 권한 (scopes)

`conversations.history` 를 쓰므로 아래 스코프가 **없으면 대조가 불가능**하고, 그 경우
자가 재시작은 동작하지 않는다(오탐 방지 때문에 죽이지 않는다). 앱 설정에서 확인한다.

| 스코프 | 대상 |
|---|---|
| `channels:history` | 공개 채널의 `conversations.history` |
| `groups:history` | 비공개 채널 |
| `im:history` | DM |
| `auth.test` | 봇 토큰 기본 — 별도 추가 불필요 |

대조 대상 채널 = `SLACK_CHANNEL_IDS` 에 설정된 채널 ∪ 실제로 이벤트를 한 번이라도 받은 채널
(DM 채널 ID 는 이벤트를 받아야 알 수 있으므로 관찰 목록이 필요다).

## 5. 운영 절차

### 5.1 재시작 후 수신 확인

재시작(자가치유·수동·배포 후 모두)을 하면 **첫 인바운드 프레임이 실제로 들어왔는지** 확인한다.
연결 완료 로그만으로는 "이벤트가 오지 않는 상태"를 구분할 수 없다(§1 의 사고가 그랬듯).

```bash
# 1) 재시작
pm2 restart <프로세스명>

# 2) 연결 완료 로그 확인
pm2 logs <프로세스명> --lines 50 | grep -E "Socket Mode 接続完了|Socket Mode error"

# 3) 첫 인바운드 프레임 확인 — hello/disconnect 가 아닌 이벤트 프레임이 있어야 한다
pm2 logs <프로세스명> --lines 200 | grep "\[Debug ws\]"

# 4) (선택) 실제 왕복 확인 — 봇을 멘션하고 응답이 오는지
```

- 3) 에서 `[Debug ws]` 줄에 `events_api` 계열 이벤트(예: `events_api app_mention`)가 보이면 **수신 정상**.
  `hello` 만 보이면 아직 이벤트가 오지 않은 것이므로 ①~③을 반복해서 확인한다.
- 4) 를 함께 수행하면 "이벤트가 오지만 처리가 안 되는" 문제와 "이벤트가 아예 안 오는" 문제를 분리할 수 있다.

### 5.2 무수신 상태 인위적 유발 → 자가 재시작 로그 확인 (배포 후 검증)

실제 장애(무수신)는 원인 미규명 상태라 자연 재현이 어렵다. 그래서 **테스트 전용 스위치**로
"인바운드 프레임이 0건" 상태를 실제 프로세스에서 만든 뒤 자가 재시작까지 확인한다.

```bash
# 1) 환경변수 하나만 켠다 (운영에서는 절대 켜지 않는다)
#    Windows: $env:SLACKBOT_SIMULATE_NO_INBOUND='1'
#    Linux  : SLACKBOT_SIMULATE_NO_INBOUND=1 pm2 restart slack-bot --update-env
pm2 restart slack-bot

# 2) 시작 로그 확인 — 소켓을 연결하지 않고 '연결된 것처럼' 동작한다
pm2 logs slack-bot --lines 20 | grep "SLACKBOT_SIMULATE_NO_INBOUND"

# 3) 대조 대상 채널( SLACK_CHANNEL_IDS 에 설정된 채널 )에서 봇을 멘션한다
#    → 슬랙에는 메시지가 생기지만 봇은 응답하지 않는다(무수신과 동일한 증상)

# 4) INBOUND_IDLE_MS(15분) 초과 후 주기 점검(5분 주기)에서 감지 → 자가 재시작
pm2 logs slack-bot --lines 200 | grep -E "무수신 감지|self-heal"

# 5) 기대 로그
#    [Bot] 무수신 감지: no inbound frames for 9xxs (socket silently stuck) — ...
#    [Bot] self-heal: no inbound frames for 9xxs (socket silently stuck) — .... Exiting so pm2 restarts.

# 6) 반드시 환경변수를 제거한다 (남으면 15분 주기 재시작 루프가 된다)
```

- 대조 채널은 `SLACK_CHANNEL_IDS` 에 설정된 채널 ∪ 이벤트를 한 번이라도 받은 채널이다.
  `SLACK_CHANNEL_IDS` 가 비어 있으면 대조 채널이 0건 → **판정 불가 → 재시작하지 않는다**(§6).
  따라서 위 검증은 `SLACK_CHANNEL_IDS` 에 최소 1개 채널이 설정된 상태에서 수행한다.
- 재현 모드에서도 **봇 멘션**(DM 불가 — DM 채널 ID 를 아직 모름) 으로 트래픽을 만들어야 한다.
- 정상 상태에서의 오탐 검증(반드시 함께 수행): 스위치 없이 15분 이상 무트래픽 상태로 두면
  `[Bot] 무수신 점검: ... (자가 재시작 안 함)` 이 찍히고 **프로세스가 죽지 않아야** 한다(§3).

## 6. 알려진 한계

- **인바운드 프레임이 전혀 오지 않으면 점검 대상 채널을 알 수 없다.** `SLACK_CHANNEL_IDS` 가 비어 있고
  이벤트를 한 번도 받지 않은 상태에서는 대조 채널이 0건 → 판정 불가 → 자가 재시작하지 않는다.
  → `SLACK_CHANNEL_IDS` 에 최소 1개 채널을 설정한다.
- **동일 앱 토큰 다중 인스턴스는 이 기능만으로 해결되지 않는다.** 같은 `SLACK_APP_TOKEN` 으로 여러 인스턴스가
  떠 있으면 이벤트가 한쪽 연결에만 배달될 수 있고, 그중 하나가 "무수신"으로 판정될 수 있다.
  재시작은 그 인스턴스의 연결을 새로 고칠 뿐, 근본 원인은 별도로 정리해야 한다(§8).
- **판정 불가(권한 없음 등) 상태에서는 아무 것도 하지 않는다.** 감지가 "조용히 비활성"인 상태가 될 수
  있으므로, 배포 후 3~4 에서 `[Debug ws]` 이벤트 프레임이 보이는지 반드시 확인한다.
- **봇이 응답할 이벤트가 아닌 트래픽은 놓쳐도 감지하지 못한다.** 앱이 `message.channels` 로 구독하지
  않고 `app_mention` 만 받는 구성이라면, 멘션 없는 채널 대화는 우리에게 이벤트로 오지 않으므로
  "놓친 트래픽"으로 세지 않는다(§3-3). 채널 구독 여부는 앱 설정에서 확인해야 하며,
  워치독은 **실제로 그런 이벤트를 받은 적이 있을 때만** 넓은 기준을 적용한다.
- **대조 대상 채널당 최근 메시지 50건까지만 본다.** 그보다 오래된 놓친 메시지는 판정 대상이 아니다.

## 7. 테스트

```bash
node --test slack-bot/tests/inbound-idle-watchdog.test.js
```

LLM·네트워크 없음(슬랙 API 는 주입한 fake). 주요 케이스:

- 임계 초과 + 트래픽 존재 → 자가 재시작 사유(`no inbound frames`) 발생
- 임계 초과 + 트래픽 없음(진짜 유휴) → 자가 재시작 **안 함**
- `auth.test` 실패 → 자가 재시작 / `auth.test` 도달 실패(네트워크) → **안 함**
- 판정 불가(unknown) → **안 함**
- 소켓 `disconnected` → 점검하지 않음
- **시계 어긋남 오탐 회귀**: 로컬 시계가 슬랙 서버보다 30초 느려도 "이미 받은 메시지"는
  놓친 것으로 보지 않는다(§3-9)
- 마지막 수신 이벤트 이후 도착한 메시지 → 트래픽으로 잡는다
- 앱이 채널 메시지 이벤트를 준 경우에만 멘션 없는 일반 메시지를 트래픽으로 본다
- 타이머 unref 정책: 기본은 unref(워치독이 프로세스를 살리지 않는다) / 재현 모드(`keepAlive`)만 참조 유지
- `index.js` 배선 계약(워치독 부착·자가 재시작 경로 연결·주기 점검 시작) 확인
- 자가 재시작 실행 증거: 자식 프로세스가 `[Bot] self-heal: no inbound frames ...` 로그를 남기고 **exit 1**

## 8. 미확인 항목 — 동일 앱 토큰 다중 인스턴스

"같은 앱 토큰으로 여러 PC 에서 같은 봇이 도는지"는 **배포 환경(각 PC) 단위** 확인이 필요하며,
이 저장소만으로는 확인할 수 없다(배포 인스턴스 목록이 이 저장소에 없다).

확인 절차(배포 담당자가 각 인스턴스에서 수행):

```bash
# 각 인스턴스에서
grep -R "xapp-" <설정 파일 경로> | sed -E 's/(xapp-[A-Za-z0-9-]{6}).*/\1.../'
# 슬랙 앱 관리자 화면에서 App-Level Token 의 사용 중인 연결/인스턴스 목록 확인
```

확인 결과는 **운영 문서에 남기고**, 같은 앱 토큰의 인스턴스가 2개 이상이면
**인스턴스를 1개로 줄이는 것**이 무수신 재발의 근본 대책이다(§6).
