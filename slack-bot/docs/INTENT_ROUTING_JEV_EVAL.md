## 0. 요약 (결론 먼저)

- **Jev 는 기존 분류기보다 낫다.** 권장 구조 ③(규칙 → Jev → LLM 폴백)이 현행 ①(규칙 → claude -p)을 **모든 지표에서 지배(dominate)**한다: 정확도 **89.5% → 92.1%**, task 재현율·question 정밀도는 양쪽 다 100% 유지, 그러면서 **불필요 이슈(사고 A) 16% → 12% 로 감소**.
- Jev 가 **실제로 라우팅한 13건은 전부 정답(오류 0)**, 같은 입력 3회 반복 **판정 일치율 100%**(비-flaky), 지연 **p50 710ms** — 현행 claude -p 분류기 **p50 8,902ms** 대비 **약 12배 빠르다**.
- **스위치를 켤 것을 권고한다**(`JEV_INTENT_ENABLED=1`). 단, 코퍼스 규모가 작으므로(아래 §5) 초기엔 섀도/모니터링과 병행한다.
- **확정 임계값**: `T_hi=0.7`, `P_hi=0.5`, `P_lo=0.2`. (사양 §5 초기 제안값 0.8/0.7/0.3 은 **근거 없는 값**이었고, 실측 스윕 곡선에서 **오류 0 을 유지하는 최저 임계값**으로 선정했다. 자세한 근거 §4.)

## 1. 산출물 위치와 재현

| 항목 | 경로 |
|---|---|
| 평가 코퍼스 | `slack-bot/eval/intent/corpus.jsonl` (1행 1케이스 JSON, 38건) |
| 평가 스크립트 | `slack-bot/eval/intent/evaluate.mjs` (node 단독, 외부 의존 추가 없음) |

재현 커맨드(sk 는 **환경변수로만** 주입 — 출력·로그에 노출되지 않는다):

```bash
GIIP_SK=<이 봇 채널의 giip sk> \
GIIP_JEV_GATEWAY_URL=https://giipfaw.azurewebsites.net/api/giipJevGateway \
node slack-bot/eval/intent/evaluate.mjs \
  --corpus slack-bot/eval/intent/corpus.jsonl --groups 1,2,3 --repeat 3 --json
```

- `--repeat 3`: 같은 입력을 Jev 에 3회 호출해 판정 일치율(flaky 여부)을 본다.
- `--json`: 끝에 `JSON_RESULT_BEGIN … JSON_RESULT_END` 로 기계 판독용 결과를 출력한다.
- 임계값을 고정해 보려면 `--t-hi 0.7 --p-hi 0.5 --p-lo 0.2`. 미지정이면 스윕으로 자동 선정한다.
- `claude -p`(대조군 ①·③ 의 LLM 단계)가 호출되므로 전체 실행에 수 분이 걸린다(LLM 건당 ~9초).

## 2. 코퍼스 구성 (일반화)

사양 §1.2 의 오분류 3유형을 일반화해 3언어(ko/ja/en)로 작성했다. 실제 사용자 문장·이슈 번호·경로는 쓰지 않았다.

| 유형 | 기대값 | 건수 | 설명 |
|---|---|---|---|
| A. 질문이 task 로 | `question` | 13 | 기존 결과 파일/URL/경로/상태의 **읽기전용 조회**인데 "파일/결과/보여줘" 명사 때문에 task 로 오분류되던 유형 |
| B·C. 작업이 question 으로 | `task` | 13 | "계산해서 보여줘 / 문서 업데이트 / 버그 고쳐 / 합계 행 추가" 등 **파일 변경이 필요**한데 부드러운 어투라 question 으로 묻히던 유형 |
| M. 모호 | `ambiguous` | 12 | 너무 짧거나 대상 불명 — 안전 폴백(이슈 안 만듦)을 기대 |
| 언어 | — | ko=14 ja=12 en=12 | 봇 사용 3언어 모두 포함 |

평가 지표는 **운영상 이진 판정**으로 접어 계산한다: 봇의 동작은 둘뿐이므로(task=이슈 등록 / question=채널 즉답), `ambiguous` 기대값은 "불필요한 이슈를 만들지 않는 것"이 정답이라 **question 쪽으로 접는다**. 대신 **모호/질문을 task 로 바꾼 비율(사고 A)** 을 따로 보고한다.

## 3. 대조군 결과

실측(origin/main, engine `jev-1.14.0`, 2026-11-04):

| 대조군 | 정확도 | task 재현율 | question 정밀도 | 사고 A(불필요 이슈) | 사고 B·C(작업 묻힘) | 폴백율 | 단계별 판정 |
|---|---|---|---|---|---|---|---|
| ① 현행(규칙 + claude -p) | 89.5% | 100.0% | 100.0% | **16.0%** | 0.0% | 84.2% | rule 6 / llm 32 |
| ② 규칙 + Jev (LLM 폴백 없음) | 81.6% | 46.2% | 78.1% | 0.0% | **53.8%** | 50.0% | rule 6 / jev 13 / fallback 19 |
| ③ 권장 전체(규칙 → Jev → LLM) | **92.1%** | 100.0% | 100.0% | **12.0%** | 0.0% | 50.0% | rule 6 / jev 13 / llm 19 |

- **정확도**: 전체 38건 중 올바르게 분류한 비율. **task 재현율**: 기대=task 중 task 로 보낸 비율(사고 B·C 의 역). **question 정밀도**: 예측=question 중 실제 question 비율(작업을 question 으로 묻으면 떨어진다). **사고 A**: 질문/모호(25건)를 task 로 보낸 비율(불필요 이슈). **폴백율**: 규칙·Jev 로 확정 못 해 LLM/안전기본값으로 내려간 비율.

읽는 법:
- **③ 이 ① 을 지배한다**: 정확도 +2.6pp, 재현율·정밀도 동일(둘 다 완벽), 불필요 이슈는 16%→12% 로 감소. 즉 Jev 를 끼운 권장 구조가 현행보다 **엄밀히 낫다**.
- **② 는 ① 보다 나쁘다**(재현율 46.2%, 작업 묻힘 53.8%). Jev 가 자신 없는 케이스를 안전하게 question 으로 떨구는데, LLM 폴백이 없으면 그 떨굼이 그대로 "작업 묻힘"이 된다. → **Jev 는 LLM 을 대체(②)하면 안 되고, LLM 앞에 덧대는(③) 구조여야 한다.** 사양 §3 의 설계 결정을 실측이 뒷받침한다.
- **잔여 사고 A(③ 의 12%, 3건)는 전부 LLM 이 판정한 건에서 나왔다** — Jev 가 라우팅한 13건은 사고 A 0. 즉 Jev 는 불필요 이슈를 줄이는 쪽으로 기여하고, 남은 불필요 이슈는 claude -p 가 모호 입력을 task 로 과판정한 것이다.

## 4. Jev 실측과 임계값 확정

### 4.1 Jev 실측
| 지표 | 값 |
|---|---|
| 호출 성공/실패 | 38 / 0 |
| 지연 p50 / p95 | **710ms / 3,257ms** (min 492 / max 3,643) |
| 반복 판정 일치율(repeat=3) | **100.0% (38/38)** — 같은 입력에 항상 같은 intent. 비-flaky |
| 건당 토큰(평균) | 입력 ~501 / 출력 ~79 |
| engine | `jev-1.14.0` |
| 참고: claude -p 지연 p50 / p95 | 8,902ms / 11,350ms |

- Jev 는 claude -p 대비 **약 12배 빠르고**(p50 710ms vs 8,902ms), **결정적**(반복 일치율 100%)이다. 현행 분류기는 반복 실행 시 판정이 갈리던 사례가 사양 §8-3 에 기록돼 있는데, Jev 는 이 코퍼스에서 흔들리지 않았다.

### 4.2 임계값 선정 근거
스윕(T_hi∈{0.6,0.7,0.8,0.85,0.9} × P_hi∈{0.5,0.6,0.7,0.8} × P_lo∈{0.2,0.3,0.4})을 ③ 구조에 적용. 선정 원칙:

1. **(1차 제약) Jev 라우팅 오류 0** — Jev 를 신뢰해 라우팅한 건이 코퍼스에서 전부 정답인 임계값만 후보로 둔다. (오류가 나는 임계값은 Jev 과신 → LLM 폴백만 못하므로 배제.)
2. **(목표) Jev 커버리지 최대** — 그 안에서 Jev 가 라우팅하는 건수를 최대화해 느리고 flaky 한 LLM 폴백 의존을 줄인다.
3. **(동률) 보수적으로 더 높은 T_hi** — 미지 입력 과신을 막는다.

| T_hi | P_hi | P_lo | Jev 라우팅(오류) | 정확도 | task 재현 | Q 정밀 |
|---|---|---|---|---|---|---|
| **0.7** | **0.5** | **0.2** | **13 (0)** ← 선정 | 92.1% | 100% | 100% |
| 0.7 | 0.6 | 0.2 | 12 (0) | 92.1% | 100% | 100% |
| 0.7 | 0.7 | 0.2 | 11 (0) | 92.1% | 100% | 100% |
| 0.8 | 0.7 | 0.3 (제안값) | 11 (0) | 92.1% | 100% | 100% |

- `T_hi=0.6` 은 라우팅 오류를 유발(스윕에서 상위 후보 밖으로 밀림)하므로 **0.7 이 오류 0 을 지키는 최저 신뢰도 문턱**이다.
- `P_hi=0.5` 는 오류 0 을 유지하면서 task 라우팅 커버리지를 최대로 준다(0.5→13건, 0.6→12건, 0.7→11건).
- `P_lo=0.2` 로 질문 라우팅 게이트를 가장 보수적으로 둔다(라우팅된 question 건의 `requires_file_change` 는 ~0.05 로 0.2 보다 훨씬 낮아 0.2/0.3/0.4 어느 쪽이든 결과는 동일 — 동률에서 가장 엄격한 0.2 선택).
- **사양 §5 제안값 0.8/0.7/0.3 대비**: T_hi 와 P_hi 를 낮춰 Jev 커버리지를 늘렸다(동일 입력에서 11→13건). 제안값도 오류 0 band 안에 있으므로, **운영상 더 보수적으로 가고 싶으면 0.8/0.7/0.3 을 써도 안전**하다(Jev 가 2건 덜 라우팅하고 그만큼 LLM 폴백이 는다). 둘 다 사고 A·B·C 0, 정확도 92.1% 로 동일하다.

### 4.3 코드 기본값과의 관계 — 변경 불필요
`slack-bot/intent.js` 의 기본값은 `JEV_INTENT_T_HI=0.8 / P_HI=0.7 / P_LO=0.3` 이며 **셋 다 오류-0 band 안**이라 안전하다(제안값이 우연히 보수적 쪽이었다). 따라서 **코드 기본값은 바꾸지 않는다**. 확정 운영점을 쓰려면 환경변수로 덮어쓴다:

```
JEV_INTENT_ENABLED=1
JEV_INTENT_T_HI=0.7
JEV_INTENT_P_HI=0.5
JEV_INTENT_P_LO=0.2
```

## 5. 한계와 권고 (정직하게)

- **코퍼스 규모가 작다(38건, Jev 라우팅 13건).** 임계값은 "근거 없는 제안값"에서 "실측으로 선정한 값"으로 올라섰지만, 이 코퍼스에 대해 오류 0 이라는 뜻이지 모든 입력에 대한 보증은 아니다. 켠 뒤 섀도/모니터링으로 실트래픽에서 Jev vs LLM 불일치를 수집해 코퍼스를 키우고 주기적으로 재평가할 것을 권고한다(판정 로그는 이미 `intent.js` 가 masked hash 로 남긴다 — 사양 §6.2).
- **잔여 사고 A(모호 입력을 task 로)는 LLM 단계의 몫**이다. Jev 커버리지가 늘면(코퍼스 확장·질문 세트 튜닝) 더 줄일 여지가 있으나 이 이슈 범위 밖이다.
- **임계값은 engine 버전(`jev-1.14.0`)에 묶인다**(사양 §10-3). engine 이 바뀌면 재평가해야 한다 — 응답의 `engine` 필드로 추적한다.
- 사양 §10 의 다른 미결(송신 데이터 보존·소재지 §10-4, 레이트리밋 §10-5)은 이 평가의 범위가 아니며 그대로 미확인으로 남는다.

## 6. 결론

권장 구조 ③ 이 현행을 지배하고 Jev 가 정확·고속·결정적이므로 **스위치 ON 을 권고**하되, 코퍼스가 작은 초기에는 모니터링과 병행한다. 확정 임계값은 **T_hi=0.7 / P_hi=0.5 / P_lo=0.2**(보수적 대안 0.8/0.7/0.3 도 안전).
