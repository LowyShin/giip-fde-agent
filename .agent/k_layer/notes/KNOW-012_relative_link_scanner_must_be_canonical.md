# KNOW-012 — 상대링크 "미존재 N건" 기준선은 스캐너가 정본이어야 성립한다

- **상태**: 확정 (2026-10-25 CSN 70424 저장소 정비 51차 세션 실측)
- **근거**: CSN 70424 저장소 정비 세션 43~51차
- **관련**: [KNOW-011](KNOW-011_markdown_relative_link_base_is_the_linked_file_location.md) · [KNOW-006](KNOW-006_repo_gates_not_wired_to_ci.md)
- **적용 범위**: 이 저장소의 마크다운 문서 상대링크 점검. 다른 저장소에도 같은 방식으로 적용 가능.

## 1. 현상

CSN 70424 저장소 정비 세션이 43차부터 매 회차 **상대링크 스캔**을 했다.
그런데 스캐너를 **매 회차 새로 짰고**, 스캐너마다 세는 대상과 제외 규칙이 달랐다.
그래서 "미존재 링크 N건" 이 회차마다 다음처럼 출렁였다.

| 회차 | 기준선(미존재 N건) | 그 회차가 쓴 스캐너 기준 |
|---|---|---|
| 43차 | 28건 | 전체 인라인 링크 중 상대 경로만 |
| 44차 | 27건 | 인라인 링크만(참조 정의 제외) |
| 45차 | 26건 | 인라인 링크만 + 스캐폴딩 24건 |
| 46차 | 11건 | 스캐폴딩 분류 기준을 바꿔서 |
| 47차 | 31건 | 백틱 코드 예시 7건 + 스캐폴딩 24건 |
| 48차 | 33건 | 스캐폴딩 24 + 코드 예시 9 |
| 49차 | 26건 | 스캐폴딩 24 + 플레이스홀더 2 |
| 50차 | 34건 | 스캐폴딩 24 + 코드 예시 9 + **실제 결함 1건** |

N이 다르다는 것은 **스캔 대상이 달랐다**는 뜻이다. 그래서 매 회차 기록마다
"N건 = 스캐폴딩 A + 코드예시 B 라고 분해해야 하며, 스캐너마다 개수가 다르므로
**개수가 아니라 분류로 판정할 것**" 이라는 문장을 다시 써야 했다 — 45·46·47·48·49·50차
모든 기록에 그 문장이 반복됐다. 같은 분류를 매번 다시 하룻밤마다 증명하고 있었다.

50차는 다른 회차와 달리 **실제 결함 1건**(49차 산출물의 깨진 링크)을 찾아 **교정했다.**
그 교정의 계기가 된 함정도 바로 이 스캔이었다:
50차 스캐너는 **코드 블록 안의 링크를 결함으로 집계**했다.
50차 산출물 KNOW-011 이 `[KNOW-009](../.agent/k_layer/notes/...)` 를 코드 펜스 안에
적어 두었는데, 그게 "깨진 링크의 예시"다. 코드 펜스를 무시하는 스캐너는
**설명 예시를 결함으로 집계**한다.

## 2. 원인

**판정 로직이 저장소에 없었다.** 매 회차가 그 회차의 맥락에서 스캐너를 짜서
(1) 판정 기준이 회차마다 달라졌고, (2) "무엇이 결함이고 무엇이 오탐인지"의
분류도 매 회차 사람이 손으로 했다. 회차가 바뀔 때마다 그 분류를 처음부터 다시论证했다.

게이트로 묶여 있지 않았으므로 실패해도 아무도 몰랐다 — 게이트 없이는
"다음 결함은 main 에 유입된 채 발견되지 않는다"(KNOW-006)이 그대로 반복됐다.

## 3. 교정 (51차)

### 3-1 스캐너를 저장소 정규본으로

`scripts/gissue/lib/relative-links.mjs` (신규) — 판정 로직의 **유일한 출처**.
매 회차가 새로 짜지 않고 이 파일을 쓴다 → **기준선이 회차와 무관하게 고정된다.**

판정 규칙 4개:

1. **코드 펜스(```/~~~)와 인라인 코드 스팬(`) 안의 링크는 링크가 아니라 "설명"이다** → 결함 아님.
   펜스 줄은 빈 줄로 대체해 **라인 번호가 원본과 어긋나지 않게** 한다.
2. **스캐폴딩** — `.agent/templates/` 와 `.agent/skills/bkit-templates/` 아래의 미존재 링크는
   "생성물이 배치된 뒤에야 성립하는 링크"다 → **디렉터리 단위로** 예외.
   파일·링크 단위 allowlist 를 만들지 않는다(항목이 늘어나면 규칙이 무너진다).
   (51차 실측: `.agent/templates/` 21건만 이 규칙에 걸렸고, `bkit-templates` 의 링크 3건은
   코드 펜스 안 예시라 **규칙 1에서 먼저 제외**됐다.)
3. **그 외 미존재 상대링크 = 실제 결함**.
4. **rule 42 준수** — 검사 대상 마크다운 0건이나 상대링크 0건이면 "통과"가 아니라 **명시적 실패**.

### 3-2 게이트에 결선

`scripts/gissue/run-repo-gates.ps1` 에 **단계 4**로 추가했다.
`node scripts/gissue/lib/relative-links.mjs` 1회 호출로, 로컬/CI 가 **똑같은 코드**를 쓴다
(rule 48 single_source_safety_predicate). CI 워크플로는 `run-repo-gates.ps1` 만 호출하므로
추가 wiring 없이 CI 에도 걸린다.

### 3-3 회귀 테스트

`scripts/gissue/tests/test-relative-links.mjs` (신규, PASS 30 / FAIL 0) —
스캐너의 **판정 규칙 자체**를 고정한다. 스캐너가 조용히 바뀌면
"스캔 결과 0건" 이나 "결함 N건" 이 틀린 근거로 다음 세션에 인계된다.

기대 건수 하한선도 함께 올렸다(ps1 20건 / **mjs 4건 → 5건**) — rule 42 의
"검사기가 조용히 사라진 테스트를 못 잡는" 계열을 막기 위해.

## 5. 다음 세션에 대한 인계

- 상대링크를 세려면 **새로 짜지 말고** `scripts/gissue/lib/relative-links.mjs` 를 쓴다.
  기준선은 **"마크다운 N개 · 전체 링크 N건 · 상대링크 N건 · 스캐폴딩 N건 · 실제 결함 N건"** 5개 수치로
  적는다. 스캐너를 바꾸면 **회차 간 비교가 무의미해지므로** 그러지 않는다.
- **개수가 아니라 분류로 판정한다** — 이 문장이 45~50차 기록에 반복됐지만,
  이제는 스캐너가 분류를 하므로 **스캐너 출력을 그대로 인계**하면 된다.
- 스캐폴딩 21건은 **전부 `.agent/templates/`** 다(51차 기준선).
  `.agent/skills/bkit-templates/` 의 3건은 **코드 펜스 안의 예시**라서 스캐폴딩조차 아니라
  아예 집계 대상이 아니다 — 즉 두 디렉터리의 처리 방식이 다르다.
  **다음 회차에 이 숫자가 바뀌면(예: 22건) 새 산출물이 생겼다는 뜻**이다 —
  템플릿 추가뿐이면 정상, 일반 문서 쪽 증가면 실제 결함 후보를 의심한다.
- **기준선 5개 수치를 그대로 인계한다** — "마크다운 N · 전체 링크 N · 상대링크 N ·
  스캐폴딩 N · 실제 결함 N". 스캐너를 바꾸지 않는 한 앞의 4개는 산출물 추가에 따라
  자연히 늘고, **스캐폴딩과 실제 결함은 늘지 않아야 한다.**
