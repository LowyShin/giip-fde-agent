# Shadow 모드도 비용이다 (giip 4334 후속)

## 핵심

의뢰 체크리스트 판정(giip 4334)의 기본 모드 Shadow 는 코멘트·상태를 쓰지 않지만, **구룰이 되돌리려는 이슈마다
판정 LLM(haiku)을 1회 호출**한다. 구룰이 같은 이슈를 같은 이유로 계속 되돌리려 하면 틱마다 같은 입력으로
반복 호출된다. 더 나쁜 것은 호출 실패·파싱 실패(`Ok=$false`)는 기록하지 않았다는 점이다 - 기록이 없으니 다음 틱에
또 호출한다(재시도 폭주). 실측(2026-11-01, 읽기 전용 dry-run): 720시간 창에서 감사한 12건 중 구룰 REVERT 2건이 Shadow
평가 대상이었고, 그중 1건은 파싱 실패였다(축소 전 코드에서는 이런 실패가 기록되지 않아 다음 틱에 다시 호출됐다).

## 설계 원칙 (구현: `scripts/gissue/gissue-audit-lib.ps1` 의 "Shadow 비용 축소" 구역)

1. **축소는 Shadow 한정.** Live 판정은 정확성이 우선이므로 캐시를 쓰지 않는다. 캐시가 Live 로 새면 입력이 같다고
   착각한 재사용이 전이를 오염시킨다. 테스트가 `Invoke-ChecklistAssessment` 본문에 Shadow 참조가 없음을 고정한다.
2. **캐시 키는 판정기가 보는 입력 전부의 해시 + 모델 + 프롬프트 버전.** 일부(예: 최신 코멘트만)로 키를 만들면 의뢰를
   바꾸는 중간 코멘트를 놓쳐 오래된 판정을 재사용한다. 전부를 해시하면 동일성이 완전 보장된다. 프롬프트를 바꾸면
   버전 상수를 올려 무효화한다.
3. **싼 검사부터.** (isn, 구룰 사유) TTL 스킵·상한·백오프는 입력 조회(API/gh)보다 먼저 판단해 조회 비용까지 아낀다.
4. **실패도 기록한다.** 실패를 판정 로그와 섞으면 통계가 오염되므로 별도 파일(`checklist-shadow-failures.jsonl`)에
   남기고 백오프한다. 성공만 기록하는 로그는 실패 재시도를 막지 못한다.
5. **여러 프로세스가 같은 jsonl 에 쓴다.** .NET `AppendAllText` 는 `FileShare.Read` 라 동시 쓰기가 `IOException` 이고,
   예전 코드는 `catch { }` 로 조용히 버렸다 - 레코드가 유실돼도 아무도 모른다. 짧은 재시도와 성공 여부 반환으로 고친다.
6. **끌 수 있어야 한다.** `GISSUE_CHECKLIST_SHADOW_REDUCE=off` 로 종전 동작을 복원할 수 있어야 축소 자체가 오판을
   숨기는지 비교할 수 있다.

7. **판정 LLM 에 한글을 stdin 으로 넘기는 스크립트는 UTF-8 을 명시 고정한다.** `review-done-audit.ps1` 에는 `pr-gate-sweep.ps1` 에 있는 `[Console]::OutputEncoding` / `$OutputEncoding` UTF-8 고정이 없어 한글이 깨진 채 `claude -p` 에 전달됐고, Shadow 판정 4건이 전부 형식 불일치(Ok=false)로 끝나 레코드가 한 건도 쌓이지 않았다. 수정 후 4건 모두 기록. 같은 계열 결함은 한 스크립트만 고치면 다른 스크립트에 남는다 - 회귀 테스트가 두 스크립트의 고정 여부를 함께 본다.
