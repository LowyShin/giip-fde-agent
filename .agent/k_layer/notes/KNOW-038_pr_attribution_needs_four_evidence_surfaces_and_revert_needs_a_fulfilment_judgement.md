# 되돌림 오판의 두 뿌리 (giip #4840/#4839)

## 핵심

"대응 PR 없음" REVIEW→READY 되돌림이 27건 이상 누적된 사고의 원인은 **두 개가 섞여 있었다.**

1. **귀속(attribution)의 탐색면이 1개뿐이었다.** 기대 head 브랜치 `bot/task-giip-<isn>` 중심의 탐색은
   레포 목록 밖(제품 레포·다른 프로젝트 레포), 비규약 브랜치(`docs/giip-4219-…`), 수동 PR,
   커밋 메시지에만 isn 이 있는 PR 을 전부 놓쳤다.
   **실측(2026-11-11): GitHub 검색은 PR 제목/본문/댓글만 색인하고 브랜치명은 색인하지 않는다.**
   → 브랜치명으로 잡으려면 브랜치를 직접 열거해야 한다.
2. **판정 단위가 "PR 유무"였다.** PR 귀속이 맞더라도 "진행 코멘트 형식" 같은 사소한 사유로
   되돌려졌다(giip #4839 — 2회 연속).

## 설계 원칙 (구현: `scripts/gissue/gissue-audit-lib.ps1` · `scripts/gissue/lib/pr-lookup.mjs`)

1. **귀속은 증거 4면** — 브랜치명 / PR 제목·본문 / 커밋 메시지 / 이슈 코멘트의 PR 링크.
   규칙 정본은 `lib/pr-lookup.mjs` 하나뿐이다(PowerShell 복붙 금지 — giip #2504 의 구조).
2. **"기대 브랜치 미탐지 단독"은 되돌림 근거가 아니다.** 다른 증거면이 더 있을 수 있다.
3. **대표(판정 대상) PR 은 "이 isn 을 브랜치/제목으로 선언한 PR"** — 본문에서만 인용한 PR 은 참조다.
   (giip #4840: 인용만 한 PR 을 판정 대상으로 삼으면 무관한 diff 로 scope MISMATCH → 오탐 되돌림.)
   커밋 메시지 경로에도 같은 좁히기를 적용한다(다른 이슈를 선언한 PR 은 제외).
4. **되돌림은 "의뢰 항목 판정이 UNFULFILLED" 일 때만.** 되돌리기 전에 판정 근거(체크리스트)를
   코멘트로 남긴다. 판정 실패·근거 부족은 **되돌리지 않는다**(rule 49 비대칭: 오탐 비용이 크다).
5. **비교 가능성** — 구룰 결론과 신룰 결론을 같은 shadow 로그 스키마로 남긴다.
   `compare-checklist-vs-legacy.ps1` 로 두 경로를 직접 비교할 수 있어야 한다.
6. **롤백 경로를 남긴다** — `-PrGateMode Gated|Shadow|Legacy`. Legacy 는 종전 동작(즉시 되돌림).

## 구현 중 실측한 함정

- `gh search prs` 의 JSON 필드에 **headRefName 이 없다** → 브랜치 증거는 `gh pr view`/`gh api` 로 따로 봐야 한다.
- `gh search prs --owner <org> -- "head:<브랜치>"` 는 **정확한 브랜치명**만 찾는다(패턴 불가).
- `gh search prs --state` 는 `open|closed` 만 받는다(merged 는 closed 에 포함, 결과의 `state` 값이 `merged`).
- **Node 정규식에 `(?i)` 인라인 플래그는 없다** — `.NET habit` 으로 쓰면 런타임 에러가 난다.
- **캐시를 링크 텍스트까지 묶어야 한다** — isn 만 키로 쓰면 "링크 없이 조회한 결과"가
  "링크 있는 조회"에 재사용돼 증거가 통째로 사라진다(PR 상태 캐시도 같은 이유로 위험).
- 조직의 모든 브랜치를 열거하면 비용이 무한대다(LowyShin 조직은 272개 레포).
  → "로컬 후보가 이 isn 을 **선언한** PR 이면 조직 전 탐색을 건너뛴다"로 비용을 0 으로 만든다.
