# 58. 엔진 호출 절감 — 토큰 소모는 호출 횟수가 결정한다

> **HARD RULE** — AI 엔진 호출의 토큰 소모는 모델 단가나 토크나이저가 아니라
> **호출 횟수와 호출당 컨텍스트 재읽기**가 결정한다.
> 배경: 2026-11-16 실측에서 동일 작업의 엔진 간 총량 차이(약 4.3배)는 토크나이저가
> 아니라 API 호출 횟수(11회 vs 42회)에서 발생했고, 호출 1회마다 누적 컨텍스트
> 전체가 캐시 읽기로 다시 계수됨을 확인했다. 운영 트래픽은 호출당 평균 약 157K
> 토큰에 캐시 읽기가 약 97~98%다.
> 실측 원본: [`docs/60-operations/token-usage-measurements.md`](../../docs/60-operations/token-usage-measurements.md)
> 근거 giip: #5438

## 기본 원리

- 총량 = Σ(호출마다의 누적 컨텍스트) 다. 신규 입력과 출력 자체는 총량의 수 %에
  불과하므로, 절감은 "무엇을 보내는가"보다 "몇 번 부르는가"에서 먼저 나온다.
- 호출당 컨텍스트 크기는 엔진이 달라도 비슷하다. 단계를 많이 밟는 실행 방식이
  그대로 총량 차이로 나타난다.

## 행동 규범

1. **스크립트 우선** — 규칙으로 판정할 수 있는 단계(정형 전이, 집계, 대조, 기록)는
   엔진을 부르지 않고 스크립트로 처리한다. 엔진은 판단이 실제로 필요한 항목에만
   쓴다 (스케줄러 본체 비AI 원칙과 같은 방향).
2. **델타 패키지** — 판단 호출에는 판단에 필요한 항목의 본문 · 최근 코멘트 · 규칙
   발췌만 패키징해 보낸다. 이슈 전체 목록이나 히스토리를 통째로 넣지 않는다.
   호출당 입력 상한을 두고, 초과하면 항목을 나눈다.
3. **한 번에 끝낸다** — 호출 전에 필요한 맥락을 처음부터 갖춰 보낸다. 중간 상태
   나열이나 계획만으로 호출을 끝내면, 같은 판단을 위해 재호출이 발생해 총량이
   배가 된다. 출력은 구조화 형식으로 받아 스키마 검증에 실패한 항목만 재호출한다.
4. **기본 모델** — MiniMax를 쓰는 모든 곳의 기본 모델은 `MiniMax-M3.1-Flash`다.
   코드 작업과 민감한 내용은 `MiniMax-M3`로 올리고, 최상위 판단(게이트 재검증 등)
   만 Claude를 쓴다. 스케줄러의 폴백 체인은
   `MiniMax-M3.1-Flash → MiniMax-M3 → claude-opus-4-8` 로 한다.
5. **effort 고정** — reasoning effort는 medium으로 고정한다. 미지정(기본값 max)
   상태로 두지 않는다. Flash의 thinking은 끌 수 없으므로 비활성화를 지정하지
   않는다 (오류가 된다).
6. **출력 규율** — 결과 요약은 짧게 쓴다. 출력은 다음 호출들의 컨텍스트로 다시
   읽혀 총량을 키운다. 장황한 중간 서술은 그 자체로 비용이다.
7. **기록 의무** — 모든 엔진 호출은 사용량 기록 경로(tKVS factor
   `scheduler_token_usage`)를 통과한다. 기록되지 않는 호출은 계측에서 사라지고,
   라우팅 판정의 근거를 없앤다.
8. **실측으로만 바꾼다** — 모델 · 라우팅 · effort 변경은 실측 근거로만 한다.
   토크나이저 비교나 동일 작업 재현 같은 측정 없이 효과를 주장하지 않는다.

## 금지 사항

- ❌ 스크립트로 판정 가능한 정형 처리를 엔진 세션에 맡기는 것
- ❌ 전체 목록 · 히스토리를 통째로 넣은 판단 호출
- ❌ effort 미지정 상태(기본 max)로 엔진을 돌리는 것
- ❌ 사용량 기록 경로를 거치지 않는 엔진 호출
- ❌ 실측 없이 모델이나 라우팅을 바꾸고 절감을 주장하는 것
