# 51 성역 에러 우회: giipApi 오류는 새 API를 만들어 회피한다 (MANDATORY)

> **HARD RULE** — 이 규칙은 다른 기본 동작보다 우선한다. 위반 금지.
> 배경: giip #1324(giipIssueCommentsV2), giip #2340(giipApi 비의존 로깅 API), giip #2462/#2484(giipApi charset 누락 보고)의实践中 확인됨.
> 이 규칙은 giip-fde-agent가 다른 프로젝트에 적용하는 경우를 위한 것이다.

## 성역 정의

이 규칙이 적용되는 **성역(sanctuary)** 파일은 다음으로 한정된다:

- `giipfaw/giipApi/run.ps1`
- `giipfaw/giipApiSk2/run.ps1`

이 두 파일과 그 직속 디렉터리는 **절대 수정 금지**이며, 이 규칙의 직접적 적용 대상이다.
giipfaw 내的其他 giipfaw 코드(shared/*.ps1, ActionflowWorker/run.ps1 등)는 **일반 프로젝트 코드**이므로
이 규칙의 성역 대상이 아니다.

## 문제: 성역에서 에러가 발견되면 어떻게 하는가

성역 파일에서 버그/오류/한계가 발견됐을 때, "성역이니까 고치지 못한다"고 무시하거나,
반대로 "성역을 직접 수정한다"고冲动하는 것 모두 잘못된 판단이다.

**올바른 원칙(giip #1215 사용자 지시, 2026-08-19):**

> "giipApiSk2/run.ps1을 수정해야 한다면 새롭게 API를 만들고 원인이 된 API호출을 새로운 API를 사용하게 할 것."

## 규칙: 성역 에러 발견 시 처리 순서

성역 파일에서 에러/버그/한계를 발견하면 다음 순서로 대응한다:

1. **SP / 프로젝트 코드 안에서 해결 가능한지 본다.** 호출부를 바꾸거나, 인자 조합을 조절하거나,
   다른 기존 API를 사용해서 문제를 회피할 수 있으면 그것으로 끝낸다.
2. **불가능하면 신규 API(엔드포인트)를 만들어 우회한다.** 기존 성역 코드는 **그대로 둔다.**
   삭제·수정·조건분기 삽입 어떤 형태든 기존 성역 파일을 바꾸지 않는다.
   새 API의 이름 관례: 실패한 기존 API 이름에 `V2`, `V3` 등 suffix를 붙인다(giip #1324 precedent).
3. **호출자를 새 API로 전환한다.** 새 API를 만들기만 하고 기존 호출부를 그대로 두면
   버그가 여전히 동작하므로 의미 없다 — 반드시 새 API를 쓰도록 호출부를 수정한다.
4. **"성역을 고쳐도 되는지 사용자에게 묻지 않는다."** 답은 이미 이 규칙에 의해 정해져 있다:
   *수정하지 않고 우회한다.* 이미 결정된 사항을 다시 질문하는 것 자체가 이 규칙의 부재로
   인한 비효율이다(giip #2484 의 실제 피해 사례参照).

## 선례 2건

**giip #1324 (2026-08-19):** 기존 `giipIssueComments` 엔드포인트가 성역이라 `loadedRole`을 받아도
버리던 문제를, **신규 `giipIssueCommentsV2` 엔드포인트**를 만들어 우회했다.
호출 경로: `scripts/gissue/lib/post-comment.js` → `scripts/gissue/lib/comment-api.js` →
`giipIssueCommentsV2`. 기존 `giipIssueComments`는 한 줄도 수정되지 않았다.

**giip #2340 (2026-08-30):** giipApi 자체 장애 시 giipApi로 기록할 수 없으므로,
**giipApi 비의존 별도 로깅 API**를 추가했다. giipApi/run.ps1은 수정되지 않았다.
