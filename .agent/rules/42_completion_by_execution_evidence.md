# 42. 완료 판정은 실행 결과로만 (Completion by Execution Evidence)

> **HARD RULE** — "등록했다 / 머지했다 / 코드에 넣었다"는 완료 근거가 아니다.
> 근거 giip: #2415 #2425 #2429 #2431 #2436 (전부 2026-09-14 실측).

## 핵심 규칙

만든 것이 **실제로 도는지 실행해서 본 출력**만 완료 근거로 쓴다.

| 만든 것 | 완료 근거로 인정되는 것 | 인정되지 않는 것 |
|---|---|---|
| 스케줄러 태스크 | 그 태스크를 강제 실행한 출력 + 대상 스크립트의 로그에 이번 실행 흔적 | 등록 성공 메시지, `LastTaskResult=0` |
| 게이트/검사기 | **일부러 차단돼야 할 입력**을 넣어 실제로 차단된 출력 | 게이트 코드가 머지됐다는 사실 |
| 기능/화면 | 라이브 응답(상태코드 + 그 변경을 식별하는 고유 문자열) | PR 머지, "구현 완료" 코멘트 |
| 규칙/문서 | 그 규칙을 로드하는 경로가 실제로 그 파일을 읽는지 확인한 출력 | 파일을 커밋했다는 사실 |

## 특히 금지 — `LastTaskResult=0` 을 근거로 쓰지 않는다

Windows Task Scheduler 의 `LastTaskResult=0` 은 "프로세스가 정상 종료했다"만 의미한다.
**가리키는 스크립트 파일이 존재하지 않아도 0 이 나온 실측 사례가 있다(giip #2431)** — 등록된 태스크가
존재하지 않는 `.ps1` 을 가리키고 있었는데 상태창은 전부 정상으로 보였다. 태스크가 실제로 일했는지는
그 스크립트 자신이 남기는 로그에서 이번 실행 타임스탬프를 찾아 확인한다.

## 특히 금지 — 검사기가 "0개 검사 후 통과"하는 것을 통과로 읽지 않는다

giip #2436: 검사기가 인자 바인딩 결함으로 **대상 0개를 검사하고 PASS 를 반환**했다. 출력이
"통과"였기 때문에 아무도 눈치채지 못했다. 따라서 검사기의 성공 출력은 반드시 **검사한 대상 수**를
포함해야 하고, 판정하는 쪽은 그 수가 0 이면 PASS 로 읽지 않는다.

> 검사기를 만들거나 고칠 때는 **기대 PASS 1건 + 기대 FAIL 1건**을 실제로 넣어 두 결과가 모두
> 나오는 것을 확인한 출력을 근거로 붙인다. PASS 만 확인한 검사기는 "항상 PASS 하는 검사기"와
> 구분되지 않는다.

## 게이트를 만들었으면 그 자리에서 돌려본다

giip #2415 #2425 #2429 #2431 #2436 — 5건 전부 "게이트를 만들어놓고 실제로 도는지 확인하지 않아
무동작"이었다. 게이트 추가 PR 의 완료 정의에는 아래가 포함된다:

1. 차단돼야 할 입력으로 실행 → 차단 출력 확보.
2. 통과돼야 할 입력으로 실행 → 통과 출력 확보.
3. 그 게이트가 실제로 호출되는 경로(프롬프트/훅/러너)에서 **한 사이클 돌려** 로그에 흔적 확인.

3번까지 못 했으면 코멘트에 "게이트 코드 머지 완료, 라이브 1사이클 미확인"이라고 **명시**하고,
`DONE` 이 아니라 [`45_gate_cap_needs_decision.md`](45_gate_cap_needs_decision.md) 의 절차를 따른다.
