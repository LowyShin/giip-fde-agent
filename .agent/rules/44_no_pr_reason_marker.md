# 44. PR 이 성립하지 않는 이슈의 탈출구 — `[NO-PR-REASON]`

> **HARD RULE** — 대응 PR 이 없는 이슈를 `REVIEW` 로 올리기 **전에** 반드시 마커 코멘트를 남긴다.
> 근거 giip: #2415 #2425 (2026-09-14 실측).

## 배경 — 읽는 쪽만 만들고 쓰라는 지시를 빠뜨린 사고

PR 완료 게이트는 "코드를 고쳤는데 PR 이 없으면 `REVIEW` 로 두지 말고 `READY` 로 되돌린다"를
강제한다. 그런데 **조사·설계·보고·캐리오버형 이슈는 원래 대응 PR 이 없다.** 이 예외를 위해
`[NO-PR-REASON]` 마커가 도입됐는데, 게이트에 **마커를 읽는 쪽만 구현되고 세션에게 마커를 쓰라고
지시하는 쪽이 누락**됐다(giip #2425 실측).

결과: PR 이 성립 불가한 이슈가 매 사이클 `REVIEW → READY` 로 되돌려지며 3회 왕복한 뒤 사람 대기로
영구 정체됐다(giip #2415). 게이트는 설계대로 동작했고, 이슈는 그 게이트를 통과할 방법을 몰랐다.

## 규칙

1. 이슈를 처리한 결과가 **코드 변경 없음**(조사 결과 보고 / 설계 결정 / 다른 이슈로 캐리오버 /
   재현 불가 판정 등)이면, `REVIEW` 전이 **직전에** 아래 형식의 코멘트를 먼저 남긴다.

   ```
   [NO-PR-REASON] <왜 대응 PR 이 없는지 한 줄>
   - 실제로 한 일: <조사/설계/판정 내용과 그 근거>
   - 후속이 있다면: <새로 등록한 이슈 번호 또는 "없음">
   ```

   **첫 줄이 반드시 `[NO-PR-REASON]` 으로 시작**해야 한다(게이트가 첫 줄을 본다).

2. 마커는 "PR 을 안 내도 되는 면죄부"가 아니다. **코드를 고쳤는데 PR 까지 못 간 경우에는 쓰지
   않는다** — 그 경우는 원래대로 `READY` 로 되돌려 다음 사이클이 PR 까지 완수하게 한다.

3. 후속 작업이 남았으면 "오너 판단 필요"로 이슈를 방치하지 말고 **새 이슈를 등록해 링크**한 뒤
   그 번호를 마커 코멘트에 적는다.

## 게이트를 구현/이식하는 쪽의 의무

읽는 쪽(마커를 보고 통과시키는 로직)과 쓰는 쪽(세션에게 마커를 남기라고 지시하는 프롬프트 문구)은
**항상 같은 PR 에서 함께 변경**한다. 한쪽만 있는 상태가 곧 이 사고다.
이식 후에는 [`42_completion_by_execution_evidence.md`](42_completion_by_execution_evidence.md) 대로
"마커 없는 PR-less 이슈"(차단돼야 함)와 "마커 있는 PR-less 이슈"(통과돼야 함) 두 입력을 모두
실행해 두 출력을 확보한다.
