# 47. 자동 정리(worktree·잔해)의 안전 요건

> **HARD RULE** — `"clean + pushed"` 만으로 삭제하지 않는다.
> 근거 giip: #2432 #2445 #2463 (2026-09-14 실측 — 자동 정리가 작업 중인 세션의 worktree 를 삭제),
> #1540 (정리 부재로 큐 전체 마비 — 정리 자체는 필요하다는 반대편 근거).

## 왜 "clean + pushed" 가 안전 신호가 아닌가

giip #2445 실측: 정리 로직이 "워킹트리가 clean 하고 브랜치가 push 됐으면 끝난 작업"으로 판정해
삭제했다. 그러나 **에이전트는 push 이후에도 CI 확인 · 머지 · 이슈 코멘트 · 문서 갱신을 한다.**
push 직후의 clean 상태는 작업의 끝이 아니라 중간 지점이다.

반대로 정리를 아예 하지 않으면 잔해가 쌓여 큐 전체가 마비된다(giip #1540 — orphan 잔해 때문에
같은 실패가 20,000회 이상 반복되며 CSN 큐 전체가 멈췄다). 그래서 **정리는 하되 아래 5가지를
전부 충족할 때만** 한다.

## 최소 안전 요건 5가지

### 1) 최근 활동 idle 가드
디렉터리 안의 **파일 최신 수정 시각**이 임계치(권장 24시간) 이내면 대상에서 제외한다.
브랜치 상태·git 상태가 아니라 **실제 파일 활동**을 본다.

### 2) `locked` 스킵
`git worktree list` 에 `locked` 로 표시된 워크트리는 무조건 건너뛴다. 잠금은 "지금 쓰는 중"이라는
명시적 선언이다.

### 3) 심볼릭 링크 / 정션 게이트
삭제 전에 대상 트리 안에 심볼릭 링크·정션이 있는지 **먼저 검사**한다. 재귀 삭제가 링크를 따라가
링크 대상(다른 저장소 전체, 다른 레포의 `.git` 등)을 지운 실측 사고가 있다.
링크가 발견되면 삭제를 중단하고 사유를 로그에 남긴다.

> [`43_delegation_safety_block.md`](43_delegation_safety_block.md) 가 권장하는 `node_modules`
> 정션 링크와 정면으로 만나는 지점이다. 링크를 쓰는 이상 이 게이트는 선택이 아니다.

### 4) 항목별 삭제 + 인접 저장소 무결성 재검증
3개 이상을 일괄 삭제하지 않는다. **한 항목 삭제 → 인접 저장소가 여전히 온전한지 확인 → 다음 항목**
순서로 진행한다. 확인 항목 예: 인접 레포의 `.git` 존재, `git -C <repo> status` 정상 응답.

### 5) 과정 검증 로그
무엇을 왜 지웠는지 / 왜 보류했는지를 접두어(예: `[ORPHAN-CLEANUP]`)를 붙여 남긴다.
"몇 개 지웠다"는 집계만으로는 잘못 지운 것을 사후에 식별할 수 없다.

## 판정은 한 곳에서만

위 5가지 판정을 두 군데에 복붙하지 않는다 — 복붙 때문에 한쪽만 고쳐져 **같은 순간에 한쪽은
보호하고 한쪽은 삭제한 사고**가 실제로 있었다(giip #2463).
상세: [`48_single_source_safety_predicate.md`](48_single_source_safety_predicate.md).

## 삭제 대상이 되기 위한 최종 조건

위 5가지 가드를 전부 통과했고, **연결된 이슈가 `DONE` 이거나 이슈 자체가 없는** 경우에만 삭제한다.
`PENDING/READY/IN_PROGRESS/REVIEW/TESTED/NEEDS_DECISION` 에 연결된 워크트리와, `git worktree list`
에 정식 등록된 워크트리는 **절대** 건드리지 않는다.

## Claude Code 격리 worktree(`.claude/worktrees/agent-*`) 계열 (giip 5175 신설)

> **정정(2026-11-14, isn=5175)** — 이 계열은 이전까지 **무조건 제외**됐다
> ("Claude Code 자체 세션 격리 메커니즘이라 완전히 별개 — 항상 제외"). 그 판단이 실제로
> 무한 누적의 원인이었다: 어떤 자동 정리 경로에도 잡히지 않아 레포당 수십 개가 쌓였다
> (2026-11-13 실측: lowyworkenv `.claude/worktrees` 27건 + `D:\temp\worktrees` 60여 건).
> **과거 판단은 남기고, 여기서 정책을 정정한다.**

이 계열은 위 5가지 안전 요건을 **동일하게** 태운다(무조건 skip 하지 않는다). 다만 판정 방식이
일반 worktree 와 달라 **두 가지가 추가**된다.

1. **"고유 커밋 없음" 판정 병행** — 이 계열의 브랜치(`worktree-agent-<id>`)는 PR 이 없는 로컬 전용
   브랜치가 대부분이라 `gh pr list --state merged` 게이트만으로는 정리 대상이 0건이 된다
   (실측 27건 중 머지 PR 이 붙은 것은 8건). 그래서 **"worktree 의 HEAD 커밋이 `origin/main` 의 조상"**
   (= 이 worktree 에 고유한 커밋이 이미 main 에 반영됨 → 내용 유실 없음) 판정을 병행한다.
   판정 불가·미반영은 모두 삭제 금지(fail-closed)다. squash 머지 브랜치는 조상이 아니므로
   PR 게이트와 서로를 보완한다.
2. **격리 메커니즘 산출물의 dirty 제외** — Claude Code 는 만든 worktree 마다 세션 권한을
   `.claude/settings.local.json` 에 기록한다(실측 27건 중 26건이 이 파일 하나 때문에 "미커밋 변경"으로
   잡혔다). 이는 **격리 메커니즘의 부산물**이지 작업 산출물이 아니다 — 산출물로 취급하면 이 계열은
   영영 정리 대상이 0건이 되어 원 문제가 그대로 남는다. 그래서 **이 파일만** dirty 판정에서 제외하고
   (제외 사실은 로그에 남긴다), **그 밖의 미커밋 변경은 어떤 경우에도 자동 삭제 금지**다.

추가로 이 계열은 idle 임계가 일반 worktree 보다 보수적(`240분` 하한)이다 — 라이브 서브에이전트가
오래 붙잡고 있는 경우를 보호하기 위함이며, "idle 가드가 실행 중 에이전트 보호를 겸한다".

정리 도구가 **못** 지우는 것(타 세션 소유 · 미커밋 산출물 · 진행 중)은
[`.agent/rules/57_worktree_cleanup_on_completion.md`](57_worktree_cleanup_on_completion.md) 절차로
**위임자(오케스트레이터)가 직접** 판단해 정리하거나 보고한다.
