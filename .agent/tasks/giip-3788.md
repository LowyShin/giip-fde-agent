## 結論(要約)

[1/2] の結論を再実測で確認した。本件は **「ソースの昇格漏れ」でも「テナント/feature flag による表示制御」でもない**。

- 年切替ボタン(giip-3089)のソースは **`main`(PROD ブランチ)に存在**する（コミット `bc16f815` が `main` の祖先であることを実測）。`dev` は `main` の祖先（`main..dev = 0`、`dev..main = 1621`）。
- 本日 2026-10-13、`main` のデプロイワークフローは **success**（run 38410349540、headSha=`e9fe269b` = main HEAD、作成 14:05:11Z）。= 「main にマージ済み・CI 成功」を満たす。
- PROD の App Service `vgt-smart-order-prod.azurewebsites.net` は giip-3089 の静的アセットを **200 で配信**（存在しない css は 404 で妥当性検証済み）。= 機能はデプロイ済み。
- 表示可否は **データ駆動**（`renderYearNav()` が `state.chartYear` 非 0 のときだけ `hidden=false`）。テナント/契約/feature flag/権限判定の出し分けは **存在しない**。STG/PROD は同一 DB 共有で STG は表示される → **データ条件は満たされている**。

したがって残る原因は **公開ドメイン `smart-order.online` の配信/ルーティング層**に限定される。本セッションの実測でも `smart-order.online` は既定 SNI で TLS 証明書ホスト名不一致（HTTP `000`）、証明書無視接続（`-k`）でも `/`・`/health/`・当該 CSS すべて **404** であり、App Service `vgt-smart-order-prod`（アセット 200）とは別ホストに当たっている。

## 2) テナント・契約による表示制御の有無

### 事実(ソース読取 / main ブランチ)

`tesk.html` の表示ロジック:
```js
function renderYearNav(){
  if (!elYnav) return;
  if (!state.chartYear){ elYnav.hidden = true; return; }   // chartYear が 0 の間は隠す
  elYnav.hidden = false;                                    // API が年を返したら表示
  elYnavYr.textContent = state.chartYear + '年';
  elYprev.disabled = !(state.chartYear > state.minYear);
  elYnext.disabled = !(state.chartYear < state.maxYear);
}
```
- 初期 `state.chartYear = 0` → `hidden`。売上サマリー API（`sales-summary-tesk`、応答に `chartYear/minYear/maxYear`）が年を返して初めて `hidden=false`。
- **テナント ID・契約・feature flag・権限判定・`env_settings` 参照・`getattr(settings,...)` による出し分けは存在しない**（`git grep -nE 'env_settings|feature_flag|tenant|契約|権限|is_enabled|getattr\(settings'` を `tesk.html` に対して実行 → 該当なし）。可視性は純粋にデータ駆動。
- 年メタデータ源は main の `app/main_system/urls.py` / `advisor/screens.py` 等に実在（本セッション `git grep -nl` で確認）。

### 推測(仮説)

- 稼働バックエンドが giip-3089 以前のイメージなら API が `chartYear` を返さず、ボタンは `hidden` のまま残り得る。ただし STG と PROD は同一 DB を共有し STG で表示される（=API が年を返している）ため、**DB/データ側の条件は満たされている**。「データが無いから隠れている」は STG 表示の事実により棄却できる。残るのは「稼働コードが古い／配信経路が別」。

- にもかかわらず公開ドメイン `smart-order.online` は別ホストで全 404（§1）。App Service `vgt-smart-order-prod` 自体はアセット 200。

### 推測(仮説) — ランク付け

1. **(B) ドメインルーティング/binding 不整合（本セッションで直接観測した事実に最も整合）**: `smart-order.online` が giip-3089 を持つ `vgt-smart-order-prod` ではなく別の Azure リソース（ASE スライス 132.220.38.112）に向いている。CI は `vgt-smart-order-prod` にデプロイするが公開ドメインはそこを指していない可能性。
2. **(A) CLAIM-355 — 稼働イメージの古さ**: 公開ドメイン配信実体が可変タグ `:prod` を使い、config 差分ゼロで Azure が新イメージを再 pull していない。CI は「デプロイ成功」でもコンテナは旧イメージ → 年メタデータを返さない API → ボタン `hidden` のまま。
3. **(C) ブラウザ/CDN の静的キャッシュ**: 古い `tesk.html`/JS がキャッシュ配信（弱い。ハードリロードで切り分け可能）。

### 復旧手順案(人手承認後に実行。本タスクでは実行しない)

> いずれも `az` と本番アクセスが必要。本セッションでは `az` 不在で未実行（保留）。

1. **稼働イメージ確認**: `az webapp config container show -n vgt-smart-order-prod -g <rg>` でイメージ digest/タグを取得し、run 38410349540 がビルドしたイメージ digest と突き合わせ。古ければ CLAIM-355。
2. **ドメイン binding 確認**: `az webapp config hostname list -n vgt-smart-order-prod -g <rg>` で `smart-order.online` が `vgt-smart-order-prod` に bind されているか確認。Front Door 使用時は `az afd origin show` / `az network front-door ...` で origin 確認。別リソースを指していれば (B) 確定。
