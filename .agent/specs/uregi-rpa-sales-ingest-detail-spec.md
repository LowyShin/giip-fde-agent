## 1. 要件(7) 失敗分類とリトライ方針の設計

### 1-1. `FcIngestRun.error_code` コード体系

1 店舗 1 run（`FcIngestRun` 1 行）を単位とし、失敗時に `error_code` を 1 つ確定する。コードは**機械可読な固定文字列**とし、詳細はマスク済みの `error_detail`（TEXT）に残す。認証情報は `error_code`/`error_detail` のいずれにも出さない（§2 マスク規則）。

| error_code | 意味 | 典型トリガ | `retry_offsets` 適用 | 即 `poison` | 他店舗への影響 |
|---|---|---|---|---|---|
| `login_failed` | ログイン不成立（資格情報誤り／ロック画面／回数超過文言検出） | ログイン後ランディング要素が時間内に出現しない、ロック文言検出 | **なし（絶対にリトライしない）** | **する**（当該アカウントを当 run で以降スキップ） | なし（当該店舗のみ確定） |
| `selector_not_found` | 想定セレクタが DOM に不在（UI 変更の疑い） | ロケータ解決失敗（§3 のセレクタ集約が返す例外） | なし（DOM 変更は再試行で直らない） | しない | なし（他店舗は継続。ただし全店連鎖時は §1-5 の早期打ち切り検討） |
| `store_resolve_failed` | 店舗（企業/担当者）コード→Uレジ内部店舗の解決失敗 | 店舗セレクタに該当店舗が無い／権限外 | なし | しない | なし |
| `no_data` | ログイン・画面遷移は成功したが対象期間の売上行が 0 件 | CSV が空／非日付行のみ | **あり（翌 offset で再取得＝正常系の遅延データ待ち）** | しない | なし |
| `timeout` | ページ遷移・操作・ダウンロードのいずれかが時間内に完了せず | `UREGI_RPA_NAV_TIMEOUT_MS` / `UREGI_RPA_SESSION_TIMEOUT_MS` 超過 | **あり（一過性の可能性）** | しない | なし |
| `download_failed` | CSV ダウンロードイベント不発・ファイル欠損・サイズ 0 | Playwright `download` 未発火、保存先に実体なし | **あり** | しない | なし |
| `parse_failed` | ダウンロード後のデコード／パース／列マッピング失敗 | UTF-16 デコード不能、必須ヘッダ欠落（§4） | なし（データ/仕様起因。再試行で直らない） | しない | なし |

#### 1-1-1. リトライ可否の判断軸（`retry_offsets` 適用対象か否か）

- 既存バッチは「対象日（当日/前日）を複数の `retry_offsets`（例: 当日・-1日・-2日…）で巡回取得する」設計を前提とする。**リトライ＝`retry_offsets` の次 offset で再び取りに行くこと**であり、同一 run 内での即時ログイン再試行ではない。
- **`retry_offsets` 適用対象（＝後日/次 offset で自然に再取得される）**: `no_data` / `timeout` / `download_failed`。いずれも「データ到着待ち」または「一過性障害」で、ログインを増やさずに次バッチ機会で回収できる。
- **`retry_offsets` 非適用（＝再試行しても直らない・するべきでない）**: `login_failed`（アカウントロック回避のため**絶対にリトライしない**。最重要）、`selector_not_found` / `store_resolve_failed` / `parse_failed`（UI/権限/データ仕様起因で、同条件の再実行は同じ失敗を生むだけ）。
- **同一 run 内の即時再ログインは全 error_code で禁止**。特に `login_failed` は検出した時点でそのアカウントを当 run の以降処理から外す（§1-3 poison）。

### 1-2. `login_failed` の即 `poison` によるロック防止（最重要方針）

- ログイン失敗を検出したら、その店舗 run を `login_failed` で確定し、**同一アカウント（企業コード単位）を当 run の残り店舗処理から即座に除外**する（`poison` 化）。これにより「誤った資格情報 × 70 回連続ログイン試行」によるアカウントロックを原理的に防ぐ。
- `poison` はアカウント単位でメモリ上の除外セットに積む。同一アカウント配下の未処理店舗は run 内で `login_failed`（理由=`account_poisoned`）として一括確定し、ログイン試行自体を行わない。
- `poison` は run スコープ（夜間バッチ 1 回）に閉じる。翌 run では解除され、資格情報修正後は自然に復帰する。永続ロックはしない（人手対応が必要なロックは Uレジ側の事象であり、本システムは「それ以上試さない」ことで悪化を防ぐ）。

### 1-3. 1 店舗の例外が他店舗を止めないことの根拠（既存資産の再利用）

- **per-store try/except**: `fc_ingest._execute_run` の `uregi` 分岐は店舗ループ内で `try/except` により 1 店舗の例外を捕捉し、その店舗を `failed`/当該 `error_code` で確定したうえで**ループを継続**する（既存の取込フローの挙動を維持）。本設計は新たな大域 try を足さず、この既存構造に error_code 確定を載せるだけとする。
- **`release_stale` の 30 分ロック解放**: 取込は店舗×日付の処理ロックを取る。RPA が途中でプロセスごと落ちてロックが残っても、既存 `release_stale`（30 分で stale ロックを解放）により次 run で自動回収される。RPA の長時間化（1 店舗数十秒〜数分）でもこの 30 分枠内に収まる想定（§1-5 の時間予算）。
- したがって「1 店舗の失敗・ハング・クラッシュ」は、(a) per-store try/except でその店舗に封じ込め、(b) stale ロックは 30 分で自動解放され、他店舗・次 run を止めない。

### 1-4. 失敗店舗の「取込状況」(`/api/fc/ingest/summary`) 表示仕様

既存 summary API のレスポンス（店舗別の最新 run 状態）に、本 RPA 失敗分類を**破壊的変更なしに**載せる。

- API レスポンス（店舗行）に `error_code` と、人間可読な `error_label`（下表の日本語）を**追加フィールドとして**含める（既存フィールドは変更しない）。
- 画面表示は **CSS 不変原則（§31）**に従い、**新クラス名のみ**で追加する（既存クラスは変更しない）。追加する表示要素とクラス名（案）:
  - 状態バッジ: `.fc-ingest-status-badge--login-failed` / `--failed` / `--no-data` / `--succeeded` 等（新規クラスのみ）。
  - 失敗理由ツールチップ: `.fc-ingest-error-reason`（マスク済み `error_detail` の要約を表示。認証情報は出さない）。
- `error_code` → 表示ラベル／色区分（色は新クラスで定義。既存 CSS 変更禁止）:

| error_code | 表示ラベル（日本語） | 色区分（新クラス） | 再取得の見込み表示 |
|---|---|---|---|
| `login_failed` | ログイン失敗（要資格情報確認・自動再試行なし） | 赤（要対応） | 「次回自動取得なし／資格情報の確認が必要」 |
| `selector_not_found` | 画面構成変更の疑い | 赤（要対応） | 「次回自動取得なし／保守対応が必要」 |
| `store_resolve_failed` | 店舗解決失敗 | 赤（要対応） | 「次回自動取得なし／店舗設定の確認が必要」 |
| `no_data` | データ未着（0 件） | 黄（経過観察） | 「次回バッチで自動再取得」 |
| `timeout` | タイムアウト | 黄（経過観察） | 「次回バッチで自動再取得」 |
| `download_failed` | ダウンロード失敗 | 黄（経過観察） | 「次回バッチで自動再取得」 |
| `parse_failed` | CSV 解析失敗 | 赤（要対応） | 「次回自動取得なし／CSV 仕様変更の確認が必要」 |
| （成功） | 取込済 | 緑 | — |

- サマリ集計: 赤（要対応）系の件数を店舗横断でカウントし、画面上部に「要対応 N 件」を新クラス `.fc-ingest-attention-count` で表示（運用者が最初に見る指標）。

### 1-5. 全店連鎖障害時の早期打ち切り（任意・設計上の保険）

- `selector_not_found` が**連続 M 件（例: 5 件）**発生したら「Uレジ側 UI 変更で全店失敗」と判断し、残り店舗のブラウザ起動を打ち切って run を早期終了する（無駄なログイン試行＝ロック誘発を避ける）。閾値 M は `UREGI_RPA_DOM_FAILFAST_THRESHOLD`（§要件9 の設定値一覧に追加）。打ち切り時は未処理店舗を `selector_not_found`（理由=`run_aborted_dom`）で確定。
- 時間予算: 1 店舗の総処理に `UREGI_RPA_SESSION_TIMEOUT_MS` の上限を設け、`release_stale` の 30 分ロック枠内に確実に収める。

## 2. 要件(8) 認証情報の暗号化と秘匿の設計

### 2-1. 既存機構の再利用（新規の秘密保管機構は作らない）— 明示宣言

- **宣言**: Uレジ資格情報（企業コード／担当者コード／パスワード）の保管・復号は、**既存機構のみ**を使う。新しい暗号化方式・新しい鍵・新しい保管テーブル・新しい復号 API は**一切作らない**。
- 再利用する既存資産:
  - `env_settings_store.encrypt()` / `decrypt()`（**Fernet**、鍵は `ENV_SETTINGS_DB_ENC_KEY`）。
  - `FcServiceCredential.ciphertext`（暗号文の格納列）/ `masked_fields`（マスク対象フィールド定義）/ `masked_tail`（末尾数桁のみ表示するマスク表現）。
- Uレジ資格情報は `FcServiceCredential`（`service='uregi'` 相当）1 行に、他 FC サービスと同形で暗号文として保管する。平文はどこにも永続化しない。

### 2-2. 復号の局所化（復号 API を作らない方針）

- **復号はバッチプロセスのメモリ内のみ**。`fetch_daily_sales` の RPA ログイン直前に `decrypt()` し、Playwright のフォーム入力に渡した後は変数を速やかに破棄する（ログ・例外・画面・一時ファイルに残さない）。
- **画面は「設定済み」表示のみ**。設定画面は `masked_tail`（例: 末尾 2〜4 桁）だけを見せ、平文・全桁は返さない。
- **復号 API を新設しない**。HTTP 経由で平文資格情報を返す経路を作らない（作ると漏洩面が増える）。設定画面の「登録済み」判定は `ciphertext` の有無と `masked_fields` のみで行う。

### 2-3. エラースクリーンショット／HTMLダンプのマスク規則（RPA 固有の新規リスク）

RPA は失敗調査のためスクリーンショット／HTML ダンプを採りたくなるが、これが**資格情報漏洩の新規経路**になる。以下を固定規則とする。

| 項目 | 規則 |
|---|---|
| パスワード input の `value` 除去 | HTML ダンプ保存前に、`input[type=password]` および企業/担当者コード入力欄の `value` 属性を**空文字に置換**してから保存する（DOM スナップショットのサニタイズ）。 |
| ログイン画面のスクショ採取禁止 | **ログインページ／認証フォームが表示されている状態ではスクリーンショットを一切採らない**（採取前に「ログイン完了ランディング要素が存在する」ことを必須条件とする）。`login_failed` のスクショは残さない。 |
| ログ出力前のマスクフィルタ | ログ出力は専用マスクフィルタを通す。資格情報値・`ENV_SETTINGS_DB_ENC_KEY`・Set-Cookie/セッショントークン・URL クエリ中の資格情報を正規表現で検出し `***` に置換。`masked_tail` 以外の桁は出さない。 |
| 採取可能な対象の限定 | スクショ／HTML ダンプを採ってよいのは「ログイン成功後の売上画面以降」に限る。かつダンプは `selector_not_found` / `parse_failed` など**UI/データ起因の失敗調査時のみ**（`login_failed` では採らない）。 |
| 保存先 | `UREGI_RPA_DIAG_DIR`（コンテナ内の一時／マウント領域。公開 Blob やログ集約先に素通ししない）。アクセスは運用者限定。 |
| 保持期間 | 既定 **7 日**（`UREGI_RPA_DIAG_RETENTION_DAYS`）。経過分は run 開始時に掃除。障害調査に足る最小期間とし長期保持しない。 |
| サイズ/件数上限 | 1 run あたりのダンプ件数・総サイズに上限を設け、ディスク逼迫と情報滞留を防ぐ。 |

### 2-4. 設計書・ログ・コミットでの資格情報非掲載

- 本書・タスクファイル・knowledge・コミットメッセージのいずれにも、実在の企業コード／担当者コード／パスワード／URL 固有値を書かない。すべてプレースホルダ（`<uregi_company_code>` 等）で表記する。
- 検証は demo テナント `vtsmodemovegetrade` の demo 専用資格情報のみで行い、`vtsmomaruei` は読み取り専用・一切触らない。

## 3. 要件(9) 保守性の設計

### 3-1. URL・セレクタ・待機条件の単一設定ファイル集約（`fc_uregi_locators.py` 相当）

- Uレジ RPA が参照する **URL・セレクタ・待機条件を 1 ファイル `fc_uregi_locators.py`（新規・実装フェーズで作成）に集約**する。`fc_uregi.py` 本体にセレクタ文字列を散在させない。UI 変更時の修正点を 1 箇所に閉じ込め、`selector_not_found`（§1）の修正を容易にする。
- 構造（擬似・データ定義のみ。実装はしない）:

```python
# fc_uregi_locators.py（構造案・擬似コード）
LOGIN = {
    "company_code": '入力欄のロール/ラベルベースセレクタ',   # type=text（企業コード）
    "staff_code":   '入力欄のロール/ラベルベースセレクタ',   # type=text（担当者コード）
```

### 3-2. `owner.u-regi.com` → リダイレクト先ホスト（`u04` 等）の動的取得

- ログイン入口は `owner.u-regi.com`（`UREGI_LOGIN_URL` で与える固定の入口）。ログイン後、Uレジは実ホスト（例: `u04.u-regi.com` 等、テナント/負荷により変動）へ**リダイレクト**する。このホストを**ハードコードしない**。
- 方式: ログイン完了時点の `page.url` から**実ホストを動的に抽出**し、以降の画面遷移 URL は**そのホスト基準＋相対パス**で組み立てる。相対パス（売上実績／エクスポート等への道順）のみを `fc_uregi_locators.py` に持ち、ホストは実行時値を使う。
- 利点: Uレジがホスト番号（`u04`→`u05` 等）を変えても設定変更不要。`UREGI_SALES_EXPORT_PATH` 等は**相対**で保持する。

### 3-3. Uレジバージョン検知と差異警告フロー

- Uレジ画面右上にバージョン表記がある（確認時 **ver 8.14.13**）。RPA は**ログイン成功後に毎回このバージョン文字列を取得**する。
- 記録先: その run の `FcIngestRun.error_detail`（成功時も情報として併記可）および専用ログ（`UREGI_RPA_VERSION_LOG` 相当／または knowledge の claim 追記運用）。
- **差異検知フロー**:
  1. 直近に観測したバージョン値（`last_seen_version`）を DB（`env_settings_shared_value` の 1 キー、§0-c）または専用テーブル列に保持する。
  2. 今回取得値 `current_version` と比較。
  3. `current_version == last_seen_version` → 通常どおり続行（記録のみ）。
  4. `current_version != last_seen_version` → **警告を出す**（取込状況画面の新クラス `.fc-ingest-version-warning` ＋ 運用ログ WARN）。「Uレジが vX→vY に更新された可能性。セレクタ破損の兆候として要確認」と表示。処理自体は継続（バージョン差＝即失敗ではない）が、`selector_not_found` 多発と併発した場合は UI 変更を強く疑う根拠とする。
  5. 人手確認後に `last_seen_version` を新値へ更新（自動更新にすると警告が 1 回で消えるため、更新は運用判断を挟む設計を推奨。最低でも「初回観測時のみ自動セット」とする）。
- この検知により、§1 の `selector_not_found` が「なぜ起きたか（＝Uレジ更新）」を運用者が即把握でき、保守対応（セレクタ更新）につなげられる。

## 4. 要件(10) CSVパース・保存方式の設計

### 4-1. デコードとパース

- **文字コード**: Uレジ売上実績 CSV は **UTF-16LE（BOM 付き）**。Python では `open(path, encoding='utf-16')`（または bytes を `.decode('utf-16')`）で **BOM（`0xFFFE`）を自動判別**してデコードする。`utf-16le` 決め打ちは BOM を文字として残すため避け、`utf-16` を使う。改行コードは CRLF/LF 双方に対応（`newline=''` で `csv` に委ねる）。
- **区切り**: TAB。`csv.reader(f, delimiter='\t')` を使う。
- **ダブルクォート解除**: 全フィールドが `"..."` で囲まれるため、`csv` の既定 quoting でクォートを解除する（`csv.reader` が自動処理）。手動 strip で二重処理しない。

### 4-2. ヘッダ名による列マッピング（インデックス決め打ち禁止）

- **1 行目をヘッダ行**として読み、**ヘッダ名（文字列）→列インデックス**の辞書を作る。以降のデータ行アクセスは必ずこの辞書経由で行い、**固定インデックス（`row[3]` 等）を使わない**。Uレジ側の列順変更・列追加に耐える。
- 必須ヘッダが欠落していたら（辞書に目的キーが無ければ）`parse_failed` で確定（§1）。どのヘッダが欠けたかを**ヘッダ名だけ**（値は出さない）`error_detail` に残す。

### 4-3. 数値正規化

- 金額・件数の `"208,723"` → **カンマ除去**して整数化（`"208,723".replace(',', '')` → `208723`）。
- 率の `"24.02%"` → **% 除去**して小数化（`"24.02%".rstrip('%')` → `24.02`）。本取込では率列は保存対象外（§4-5）だが、将来利用に備え正規化規則だけ定義。
- 空文字／`-`／全角スペース等は欠損として扱い、保存対象列では NULL または 0（列ごとに §4-5 で規定）。

### 4-4. 非日付行のスキップ判定

- CSV には明細日付行のほか、`TOTAL` 行・`MD35週`（週計）等の**集計/見出し行**が混在する。
- **判定規則**: 列マッピングで得た `当年日付` 相当フィールドの値が **`^\d{8}$`（8 桁数字 = `YYYYMMDD`）正規表現にマッチする行だけをデータ行**として採用し、それ以外（`TOTAL` / `MD35週` / 空行等）は**スキップ**する。
- スキップ件数は run の情報としてカウントし、全行スキップ（＝データ 0 件）は `no_data`（§1、`retry_offsets` 適用）で確定。

### 4-5. 保存方式（`FcSalesDaily` UPSERT）と 16 列対応表

- **保存先**: `FcSalesDaily`。**ユニーク制約 `(store_id, business_date, source)`**、`source='uregi'`。同一店舗・同一営業日の再取得は **UPSERT**（既存行を更新）で冪等化し、まとめ取り・`retry_offsets` 再実行で重複行を作らない。
- **営業日**: `当年日付`（`YYYYMMDD`）を `business_date`（DATE）へ変換。
- **16 列 → カラム対応表**（Uレジ CSV の代表 16 列を想定。実列名は実データのヘッダで最終確定するが、マッピングはヘッダ名基準で行う）:

| # | CSV ヘッダ（想定名） | 正規化 | 保存先 `FcSalesDaily` 列 | 備考 |
|---|---|---|---|---|
| 1 | 当年日付 | `^\d{8}$` 判定後 DATE 変換 | `business_date`（キー） | 非日付行はスキップ（§4-4） |
| 2 | 当年実績（売上） | カンマ除去→整数 | **`sales_amount`（売上）** | 主指標 |
| 3 | 当年客数 | カンマ除去→整数 | **`guest_count`（客数）** | 主指標 |
| 4 | 当年客単価 | カンマ除去→数値 | （保存せず／派生値） | 売上÷客数で再計算可のため非保存を既定 |
| 5 | 前年日付 | — | （保存しない） | 比較表示用。取込対象外 |
| 6 | 前年実績 | カンマ除去→整数 | （保存しない） | 同上 |
| 7 | 前年客数 | カンマ除去→整数 | （保存しない） | 同上 |
| 8 | 前年客単価 | カンマ除去→数値 | （保存しない） | 同上 |
| 9 | 実績前年比 | % 除去→数値 | （保存しない） | 派生指標 |
| 10 | 客数前年比 | % 除去→数値 | （保存しない） | 派生指標 |
| 11 | 客単価前年比 | % 除去→数値 | （保存しない） | 派生指標 |
| 12 | 当年累計実績 | カンマ除去→整数 | （保存しない／要判断） | 累計は再計算可。既定は非保存 |
| 13 | 当年累計客数 | カンマ除去→整数 | （保存しない／要判断） | 同上 |
| 14 | 前年累計実績 | カンマ除去→整数 | （保存しない） | 同上 |

#### 4-5-1. `tran_count`（取引件数）の扱い — 明示判断

- **問題**: Uレジ売上実績 CSV には**取引件数（レシート枚数）列が存在しない**（代表 16 列は実績・客数・客単価・前年比・累計で構成され、取引件数の独立列が無い）。既存 `FcSalesDaily` に `tran_count` 列がある場合、何を入れるか。
- **設計判断（既定）**: **`tran_count` は `NULL`（source='uregi' では未取得）とする**。理由:
  - Uレジ CSV は「取引件数」を提供しないため、他源（スマレジ等）由来の `tran_count` と意味が揃わない値を混入させると、`source` 横断の集計で**取引件数が過小/不整合**になる。
  - 「客数（`guest_count`）で代替」する案は、客数＝来店人数であり取引件数（会計回数）とは定義が異なるため**代替しない**。意味の異なる値を同一列に詰めるのは §検証対象-手段一致の観点でも誤り。
- **結論**: `source='uregi'` 行の `tran_count` は NULL。取引件数が業務要件になった場合は、Uレジで取引件数を出す別 CSV／別画面の調査を**別イシュー**で起票する（本設計では NULL 固定を正とし、客数代替は採らない）。

### 4-6. 冪等性と部分取得の回復

- UPSERT キー `(store_id, business_date, source='uregi')` により、まとめ取り（1 ログインで月範囲）で同一日が複数回現れても 1 行に収束。
- RPA 途中失敗で一部日付しか取れなくても、`retry_offsets`（§1）の次 offset／次 run で欠損日が補完され、取得済み日は UPSERT で上書きされるだけ（重複増加なし）。

## 5. 横断リスク（本書担当範囲に関わるもの・giip-3710 §5 を補強）

- **アカウントロック（最重要）**: §1-2 の `login_failed` 即 `poison`＋リトライ禁止が本書の中核防御。`retry_offsets` はログインを増やさない error_code（`no_data`/`timeout`/`download_failed`）にのみ適用し、`login_failed` には**絶対適用しない**。
- **スクショ/ダンプ経由の資格情報漏洩（RPA 固有）**: §2-3 のマスク規則。特に「ログイン画面スクショ全面禁止」「HTML ダンプのパスワード value 除去」。
- **Uレジ UI 変更**: §3-1 セレクタ集約＋§3-3 バージョン検知警告で早期把握。§1-5 の連鎖打ち切りでロック誘発を防ぐ。
- **列順変更耐性**: §4-2 ヘッダ名マッピングで固定インデックス依存を排除。
