## 2. 要件(2) 店舗特定ロジック【決定】

### 2-1. 課題

Uレジはログイン後、1 アカウント（企業コード）配下に**複数店舗**が紐づく。売上 CSV を取る前に「どの店舗の売上を取得するか」を 1 店舗に特定する必要がある。店舗選択 UI はチェックボックス一覧で `コード: 店舗名`（例 `001: 渋谷店`）の形で表示される。誤って別店舗や管理者用の集約店舗を選ぶと、別店舗の売上が `FcSalesDaily` に混入する。

### 2-2. 主案（確定）

**`FcServiceCredential.external_store_id`（既存カラム・Phase 1-A で未使用）にUレジ側店舗コード（例 `001`）を保持し、ログイン後の店舗一覧を `code: name` でパースしてコード完全一致で 1 店舗だけ選択する。**

処理手順（`fetch_daily_sales` 内部・RPA）:
1. ログイン成功後、店舗選択画面の全チェックボックス行を取得する。
2. 各行ラベルを `^\s*(?P<code>\S+)\s*[:：]\s*(?P<name>.+?)\s*$` でパースし、`code`（ゼロ詰め文字列のまま）と `name` を得る。全角コロン `：` と半角コロン `:` の両対応。
3. §2-3 の除外フィルタを適用して候補集合を作る。
4. `external_store_id` と `code` を**文字列完全一致**で突き合わせる（`"001" == "001"`。前ゼロを落とす数値比較はしない — `1` と `001` を同一視すると `010`/`100` 等で誤爆するため）。
5. 一致が**ちょうど 1 件**なら、そのチェックボックスのみを選択して次工程（期間指定）へ進む。

> 設計判断の根拠: 店舗名は改称され得る（giip 既往事例あり）が、Uレジ店舗コードは原則不変。よって**コードを突合キー**にする。`external_store_id` は Phase 1-A で未使用の既存カラムであり、新カラム追加なしに保持できる（スキーマ変更最小化）。

### 2-3. フォールバック規則（確定・明文化）

| 状況 | 判定 | error_code | リトライ |
|---|---|---|---|
| ①`000` 等の管理者用/集約店舗 | **候補から除外**（下記フィルタ） | — | — |
| ②突合候補 **0 件** | フェイルファスト | `store_resolve_failed` | **しない** |
| ③突合候補 **2 件以上** | フェイルファスト | `store_resolve_failed` | **しない** |
| ④`external_store_id` が空/未設定 | フェイルファスト（初回未設定） | `store_resolve_failed` | **しない**（初回設定導線 §2-4 へ誘導） |

- **除外フィルタ**: `code` が `UREGI_STORE_EXCLUDE_CODES`（既定 `000`）に該当する行、および全角/半角いずれかの "全店"/"管理"/"本部" 等の集約名パターン（`UREGI_STORE_EXCLUDE_NAME_REGEX`、運用で調整可）に該当する行を候補から外す。除外はログに**件数のみ**残す（店舗名の秘匿は不要だが冗長ログを避ける）。
- **フェイルファストは「リトライしない」**。店舗特定は UI/権限/設定起因であり、同一 run 内で再試行しても結果は変わらない（3709 CLAIM-URG-102 と整合）。`store_resolve_failed` は `retry_offsets` 非適用コードに分類する。
- 1 店舗の `store_resolve_failed` は**他店舗の処理を止めない**（per-store try/except、3709 CLAIM-URG-103）。

### 2-4. 初回設定導線（確定・設計のみ）

初回は `external_store_id` が未設定のため、人が紐付ける導線を用意する。

- 新 API（設計上の記述。実装は別フェーズ）: `GET /api/fc/uregi/stores?credential_id=<id>` — 指定資格情報で**ログイン→店舗一覧取得→除外フィルタ適用後の候補 `[{code, name}]` を返却**（売上 CSV は取得しない軽量フロー）。この呼び出しも 1 回のログインを消費するため、**ログイン回数予算に含める**（§7-2）。
- 画面: 候補一覧をプルダウン/ラジオで提示し、人が選んだ `code` を `external_store_id` に保存する。表示追加は**新クラス名のみ**（CSS 不変 §31、例 `.fc-uregi-store-picker`）。既存 CSS は変更しない。
- 返却に実在の店舗名が含まれ得るが、**資格情報（企業コード/担当者コード/パスワード）は返却にもログにも含めない**。

## 3. 要件(3) 取得日付範囲【決定】

### 3-1. 課題

単日（当日−1）だけを取ると、Uレジ側の**締め後修正**や **MD 週（マーチャンダイジング週）確定**で過去日の数値が後から変わった分を取り込めない。一方で毎回ログインして単日ずつ取るとログイン回数が膨らみ**アカウントロック**リスクが上がる。

### 3-2. 軸案（確定）

**当日基準で遡及 N 日（既定 35 日。運用で「当月＋前月」に切替可）を毎回再取得し、`FcSalesDaily` を UPSERT で上書きする。** かつ**1 回の検索で月範囲をまとめ取りし、ログインを 1 店舗 1 回に抑える。**

- 期間: `target_date_to = 当日`、`target_date_from = 当日 − (N−1)`。既定 `N = 35`（`UREGI_INGEST_LOOKBACK_DAYS`）。「当月＋前月」運用時は月初境界で範囲を算出する（`UREGI_INGEST_LOOKBACK_MODE = days | month_pair`）。
- `N=35` の根拠: 月次の締め（前月分の確定が当月上旬まで動く）＋ MD 週（最長 5 週＝35 日）を 1 範囲で吸収できる最小日数。
- **まとめ取り**: 店舗選択後、期間を `from`〜`to` の一括レンジで指定して CSV を 1 回エクスポートする。日ごとにログイン/検索を繰り返さない（ログイン 1 回・検索 1 回・CSV 1 本）。これが §7 アカウントロック対策の根幹。

### 3-3. UPSERT 冪等性

- 保存キーは `FcSalesDaily (store_id, business_date, source='uregi')` のユニーク制約への UPSERT（3709 CLAIM-URG-113 と整合）。
- 遡及範囲が日々重複しても（昨日の run と今日の run で 34 日ぶん重なる）、UPSERT で**上書き**されるため重複行は増えない。締め後修正は「後勝ち（最新 run の値）」で反映される。
- RPA 途中失敗で部分取得になっても、翌 run の遡及範囲が欠損日を再カバーするため自己修復する。

### 3-4. `is_confirmed`（速報/確定）フラグ運用【確定】

Uレジ CSV の当年実績は、締め前は**速報**、締め後は**確定**になり得る。`FcSalesDaily.is_confirmed`（追加検討カラム）の運用規則を次のとおり定める。

- **判定基準**: 取得した `business_date` が「確定境界日」以前なら `is_confirmed = true`、より新しければ `false`（速報）。確定境界日は `当日 − UREGI_CONFIRM_LAG_DAYS`（既定 7 日 = 一般的な月締め猶予の保守値）。
  - 例: 既定 `UREGI_CONFIRM_LAG_DAYS=7` のとき、`当日−8` 以前の日付行は確定、`当日−7`〜`当日` は速報。
- **UPSERT 時の遷移**: `false(速報) → true(確定)` は許可（締めが進んだ）。`true → false` への巻き戻しは**原則禁止**（既に確定した日を速報へ戻さない。誤取得検知のため WARN ログのみ残す）。
- **用途**: 画面・レポートで速報/確定バッジを出し分け（新クラスのみ、§31）。確定済み日の数値は原則変わらない前提で下流集計のキャッシュ可否判断に使う。
- `is_confirmed` カラムが実スキーマに無い場合は、実装フェーズで追加（デフォルト `false`）するか、当面「全行速報扱い（フラグ無し）」で先行し後続イシューで追加する。**本タスクは設計の明文化のみ**で DDL は発行しない。

## 4. 要件(4) 税集計方法【3案比較 → 推奨1案を確定】

### 4-1. 課題

Uレジ CSV の「当年実績」列は、画面設定により**税抜 or 税込のどちらか一方**しか出力されない（同一エクスポートで両方は取れない想定）。一方 `FcSalesDaily` には `sales_excl_tax`（税抜）と `sales_incl_tax`（税込）の**両カラム**がある。両方を埋めたい／片方で足りる、のトレードオフをログイン回数（＝アカウントロックリスク）と突き合わせて決める。

### 4-2. 3案

| 案 | 内容 | ログイン/検索回数（1店舗あたり） | 長所 | 短所 |
|---|---|---|---|---|
| (a) 税抜固定・片側のみ | 税抜で 1 回取得し `sales_excl_tax` のみ埋める。`sales_incl_tax` は NULL | **ログイン 1 / 検索 1** | 最小負荷。ロックリスク最小 | 税込列が常に空。税込が要る下流は別途計算要 |
| (b) 両方取得（2回検索） | 税抜設定で 1 回・税込設定で 1 回、計 2 回エクスポートし両列を埋める | ログイン 1 / **検索 2**（設定切替を挟む）| 両列が実測値で揃う | 検索 2 回でセッション長が延び DOM 操作が倍。設定切替 UI の破壊に脆弱。所要時間ほぼ倍 |
| (c) 店舗ごと設定 | 店舗ごとに (a)/(b) を選択可能にする | 店舗により 1〜2 | 柔軟 | 設定・テスト・保守コストが店舗数ぶん増。障害時の切り分けが複雑 |

### 4-3. ログイン回数・所要時間トレードオフ（数値）

70 店舗、1 店舗あたりのブラウザ操作所要を「ログイン＋店舗選択＋期間指定＋CSV1本＝約 40〜90 秒」とする（§5-3 の試算根拠と共通）。

- (a): 検索 1 回 → 1 店舗 **約 40〜90 秒**。70 店舗で後述 §5-3 の総所要そのまま。
- (b): 検索 2 回（設定切替＋2 本目エクスポート追加 約 +25〜60 秒）→ 1 店舗 **約 65〜150 秒**。70 店舗の総所要が **約 1.6〜1.7 倍**。DOM 操作点が増え `selector_not_found` 面積も拡大。
- **ログイン回数はどの案も 1 店舗 1 回で不変**（検索回数だけが増える）。アカウントロックの直接要因はログイン回数なので (b) でもロックリスクは (a) と同等。ただし**セッション長延伸＝タイムアウト/DOM 変更被弾の確率増**という別リスクが乗る。

### 4-4. 推奨【確定】＝ (a) 税抜固定・片側のみ

**推奨は (a)。** `sales_excl_tax` を税抜で埋め、`sales_incl_tax` は当面 NULL とする。

根拠:
1. **税抜が会計・原価分析の基準**として下流で最も使われ、税込は税率が既知なら算出可能（将来、税率マスタ併用で `sales_incl_tax` を派生計算する余地を残す）。
2. (b) は所要時間 1.6〜1.7 倍かつ設定切替 UI への依存で**保守脆弱性が増える**割に、得られる税込実測の価値が限定的。夜間バッチ枠（§5-3）の逼迫も招く。
3. (c) は柔軟だが 70 店舗規模で設定/テスト/障害切り分けコストが見合わない。
4. 税込実測が業務要件として確定した場合は、(a) を既定に保ったまま**オプトインで (b) を店舗単位に開く**拡張（実質 (c) の限定版）を**後続イシュー**で検討する。本タスクでは (a) に一本化。

> UPSERT 時、`sales_incl_tax` は (a) では書き込まない（既存値を温存。過去に (b) 等で入った税込を NULL 上書きしない）。

## 5. 要件(5)(6) スケジュール・並列数【決定・数値試算込み】

### 5-1. 構成（新規スケジューラを作らない・相乗り）

```
既存 15分間隔ディスパッチャ（cron/タイマー, 変更しない）
        │  毎 15 分起動
        ▼
  FcIngestSetting を参照
   ├ ingest_time        … 夜間起動時刻（例 02:00）。この時刻を跨いだ最初のディスパッチで当日分 run を生成
   ├ retry_offsets      … 失敗店舗の再試行オフセット（no_data/timeout/download_failed のみ適用, 3709 CLAIM-URG-102）
   ├ service_concurrency… 同時実行ワーカー数（RPA は 2〜3 を上限, §5-2）
   ├ spread_minutes     … 起動分散幅（ログイン集中回避, §5-2）
   └ batch_size         … 1 ディスパッチで投入する店舗数の上限
        ▼
  uregi 分岐（fc_ingest._execute_run）
   └ 対象店舗を queue へ → 各ワーカーが 1 店舗ずつ RPA（§6）
        - 1 店舗 = ログイン1 / 店舗選択 / 期間まとめ取り(§3) / CSV1本 / UPSERT / ログアウト
```

- **新規スケジューラは作らない**。既存 15 分ディスパッチャが `FcIngestSetting` を読んで起動タイミング・分散・並列度・バッチサイズを決める。
- `ingest_time` を跨いだ最初の 15 分スロットで当日 run を生成し、`spread_minutes` の範囲で店舗投入を散らす。

### 5-2. 並列数の推奨上限と分散（確定）

- **`service_concurrency` 推奨上限 = 2〜3**。根拠: RPA はヘッドレス Chromium を 1 店舗 1 プロセス相当で使い CPU/メモリ消費が大きい。さらに**同一アカウント（企業コード）は必ず直列（実質 1）**とし（並列ログインはロック誘発の最大要因）、`service_concurrency` の並列はあくまで**別アカウント間**にのみ適用する。
- **`spread_minutes` によるログイン分散**: 70 店舗のログインが数分に集中するとロック検知に引っかかりやすい。`spread_minutes`（例 30〜60 分）に店舗投入をジッタ付きで散らし、瞬間ログイン密度を下げる。店舗間には `UREGI_RPA_INTER_STORE_DELAY_MS`（ジッタ付き、3710 §4）も併用。
- `batch_size` は 1 ディスパッチ（15 分スロット）あたりの投入上限。`service_concurrency × 1スロットで捌ける店舗数` を超えないよう設定し、積み残しは次スロットへ繰り越す。

### 5-3. 総所要時間の試算【数値・楽観/悲観】

前提値（1 店舗あたり、ログイン1＋店舗選択＋期間まとめ取り＋CSV1本＋UPSERT＋ログアウト）:

| シナリオ | 1 店舗所要 | `service_concurrency`（別アカウント並列） | 店舗間ディレイ |
|---|---|---|---|
| 楽観 | 40 秒 | 3 | 平均 10 秒 |
| 悲観 | 120 秒（DOM 待ち・CSV 生成待ち・リトライ無し） | 2 | 平均 30 秒 |

**総所要時間 ≒ ⌈70 / concurrency⌉ ×（1店舗所要 ＋ 店舗間ディレイ）**（同一アカウント直列制約により、実効並列は「別アカウント数」が上限。下式は別アカウントが concurrency 以上あると仮定した上限ケース）:

- **楽観**: ⌈70/3⌉ = 24 直列段 ×（40 + 10）秒 = **1,200 秒 ≒ 20 分**。
- **悲観**: ⌈70/2⌉ = 35 直列段 ×（120 + 30）秒 = **5,250 秒 ≒ 87.5 分 ≒ 1 時間28分**。

- 楽観 **約 20 分** / 悲観 **約 88 分**。悲観でも `spread_minutes`（30〜60 分）と組み合わせれば深夜帯（例 02:00〜04:00 の 2 時間枠）に収まる見込み。
- **注意（同一アカウント直列の効き）**: もし 70 店舗が少数アカウントに集中（例 1 アカウントに 70 店舗）する場合、実効並列は 1 に落ち、悲観は 70 ×（120+30）= 10,500 秒 ≒ **175 分 ≒ 約 2 時間55分** まで伸びる。**アカウント分布が総所要を支配する**ため、実装フェーズで demo テナントの実測とアカウント分布の確認を先行させる（§9 検証）。

### 5-4. 夜間ウィンドウ超過時

総所要が夜間枠を超える懸念がある場合、(1) `spread_minutes` を広げて密度を下げる、(2) 別アカウントが十分あるなら `service_concurrency` を 3 まで上げる、(3) 遡及日数 `N` を縮める（§3、ただし締め吸収と要トレードオフ）、の順で調整する。**ロックリスクを上げる「ログイン回数を増やす方向（単日化・同一アカウント並列化）」は採らない。**

## 6. 要件(E) 既存コードとの接続方針【方針確定・実装はしない】

- 既存 `fc_uregi.py` は HTTP API 前提。RPA 方式はこれを覆すが、**`verify_auth(credential)` / `fetch_daily_sales(credential, date_from, date_to)` のシグネチャを維持**し、内部実装だけ RPA（Playwright）に差し替える。戻り値の売上明細行の形は既存 `fc_sales.py` の UPSERT が期待する形に合わせる。
- `fc_ingest._execute_run` の `uregi` 分岐は「対象店舗の列挙 → 各店舗で `fetch_daily_sales` 呼び出し → `fc_sales` UPSERT」の既存フローを維持する。本設計で増える責務（店舗特定 §2・期間まとめ取り §3・税抜固定 §4）は**すべて `fetch_daily_sales` 内部に閉じ込め**、分岐側の変更を最小化する。
- セレクタ・URL・待機条件は 3709 CLAIM-URG-107 のとおり実装フェーズで単一ファイル `fc_uregi_locators.py`（新規）へ集約する。本書 §2〜§5 の決定はその定数・分岐の設計入力となる。
- Playwright 既存資産（`tools/demo-autopilot/src/lib/session.ts`、`scripts/package.json`）の再利用可否、smart-order `Dockerfile` へのブラウザ同梱可否は 3710 §5-3 で論じ済み（**論じるのみ・本タスクで Dockerfile は変更しない**）。

## 7. リスク章（最重要）

### 7-1. アカウントロック（最大リスク・最強明記）

- **ログイン失敗時はリトライしない**（固定方針。`UREGI_RPA_RETRY_ON_LOGIN_FAILURE` は既定 false を維持し true にしない。3709 CLAIM-URG-101/102 と整合）。`store_resolve_failed`（§2-3）も同一 run 内で再試行しない。
- **1 店舗 1 回ログイン＋月範囲まとめ取り（§3-2）がログイン回数削減に直結**し、ロックリスクを根本的に下げる。税集計 (a) 片側のみ（§4-4）も検索 1 回でログイン密度を上げない選択。
- **並列はアカウント間のみ**。同一アカウント（企業コード）は必ず直列（§5-2）。`service_concurrency` は 2〜3 を上限。
- `spread_minutes` と店舗間ディレイ（ジッタ付き）で瞬間ログイン密度を下げる（§5-2）。
- ロック検知時は当該アカウントをその run で以降スキップ（3709 CLAIM-URG-101）。

### 7-2. run-now 同期タイムアウト（非同期化の必要性）

- `run-now` の `budget_seconds=30` は HTTP API 前提値。RPA は 1 店舗で **40〜120 秒以上**（§5-3）かかるため、**同期実行では必ずタイムアウトする**。
- 対処: **非同期キュー投入＋ポーリング表示**（3710 §1-(11)・§3-2）。run-now は同期で走らせず `job_id` を即時返却し、画面はポーリングで進捗表示（新クラスのみ §31）。
- 初回設定の店舗候補取得 API（§2-4）も 1 ログインを消費するため、ログイン回数予算に算入し、同様に時間がかかる前提で UI を設計する（同期で即応答を期待しない）。

### 7-3. 店舗誤特定による他店舗データ混入（中）

- コード完全一致＋候補 0/複数のフェイルファスト（§2-3）で誤選択を防ぐ。前ゼロ数値比較の禁止（§2-2 手順4）で `001`/`010`/`100` の取り違えを防ぐ。
- 管理者/集約店舗（`000` 等）の除外フィルタ（§2-3）で全店集計の混入を防ぐ。

### 7-4. 遡及まとめ取りの負荷（中）

- 遡及 35 日のレンジ CSV はデータ量が増え、CSV 生成待ち・パース時間が延びる。§5-3 悲観値に織り込み済み。`UREGI_RPA_SESSION_TIMEOUT_MS`（30 分枠、3709 CLAIM-URG-103）内に収める。

## 9. 検証計画（記載のみ・本タスクでは実行しない）

> **前提**: demo テナント `vtsmodemovegetrade` のみ。**`vtsmomaruei` は読み取り専用・一切触らない**。実在の認証情報は使わずプレースホルダ／demo 専用資格情報で行う。

実装フェーズでの手動検証手順（要件(2)-(6)固有）:
1. **(2) 店舗特定**: demo アカウントに複数店舗を紐づけ、`external_store_id='001'` で run → `001` のみ選択され `010`/`100` が選ばれないこと。`external_store_id` を未設定にして `store_resolve_failed`（リトライなし）で確定し他店舗が巻き込まれないこと。`000` 等が候補から除外されること。
2. **(2) 初回導線**: `GET /api/fc/uregi/stores` が除外後候補 `[{code,name}]` を返し、資格情報が返却・ログに出ないこと。
3. **(3) 遡及 UPSERT**: `N=35` で 2 日連続 run し、重複行が増えないこと（冪等）。前日の数値を Uレジ側で修正した体で再 run し「後勝ち」で上書きされること。`is_confirmed` が境界日で `true/false` に分かれ、`true→false` 巻き戻しが起きないこと。
4. **(4) 税集計**: `UREGI_TAX_MODE=excl` で `sales_excl_tax` のみ埋まり `sales_incl_tax` が NULL（または既存値温存）であること。
5. **(5)(6) 並列/スケジュール**: `service_concurrency=2〜3`・`spread_minutes` 設定で、同一アカウントが直列化され並列ログインが起きないこと。demo の少数店舗で総所要を実測し §5-3 試算との乖離を確認。
6. **(7) run-now 非同期**: `store_id` 指定 run-now が **30 秒以内に `job_id` を即時返却**し同期タイムアウトしないこと。

検証は demo テナントに閉じ、ログ・画面に認証情報が出ないことを併せて確認する。
