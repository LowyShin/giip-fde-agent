# 엔진 토큰 소모 실측 자료 (2026-11-16)

> 목적: 엔진(MiniMax / Claude) 토큰 소모의 구조를 실측으로 확정하고, 절감 지렛대의
> 우선순위를 근거와 함께 남긴다. 설계는
> [token-usage-metering.md](token-usage-metering.md), 행동 규범은
> [`.agent/rules/58_engine_call_minimization.md`](../../.agent/rules/58_engine_call_minimization.md)
> 가 정본이며, 이 문서는 그 근거 수치의 원본이다.
> 모든 수치는 2026-11-16에 실제로 집행한 측정의 결과이며, 추정에는 추정이라고 적었다.

## 0. 요약

- 토크나이저만으로는 엔진 간 총량 격차를 설명할 수 없다. 같은 문장에서 오히려
  Claude가 MiniMax보다 토큰을 많이 센다 (실측 A).
- 같은 작업을 양쪽 엔진으로 수행하면 총량은 MiniMax가 Claude의 약 2.9~4.9배다.
  차이는 토크나이저가 아니라 **API 호출 횟수**에서 발생한다 (실측 B).
- 운영 트래픽의 총량은 "호출 횟수 × 호출당 캐시 재읽기"로 구성된다. 신규 입력과
  출력 자체는 총량의 수 %에 불과하다 (실측 C).
- 따라서 1차 절감 지렛대는 모델 교체가 아니라 호출 횟수 절감(스크립트 우선 ·
  판단 게이트 · 델타 패키지)이며, 모델 선택(기본 Flash, effort 고정)은 2차 지렛대다.

## 1. 실측 A — 토크나이저 단독 비교

### 방법

- 테스트 문장: 한국어 944자 (2,306바이트) 1종.
- MiniMax는 공개 토크나이저(HuggingFace `MiniMaxAI/MiniMax-M3` 및
  `MiniMax-M3.1-Flash` — 두 tokenizer.json의 SHA-256이 동일함을 확인, 즉 같은
  토크나이저)로 로컬 계수했다.
- 라이브 대조는 양쪽 엔진에 같은 문장의 1배본과 4배본을 각 1회씩 보내고,
  복사본당 순수 입력 토큰을 (4배본 총입력 − 1배본 총입력) / 3 으로 구했다
  (하네스 고정 오버헤드를 상쇄하는 차분법). 재시도는 하지 않았다.

### 결과

| 대상 | 복사본당 입력 토큰 | 비고 |
|---|---|---|
| MiniMax M3 (로컬 계수) | 443 | 0.469 토큰/자 |
| MiniMax M3 (라이브) | 439 | 로컬 계수와 4토큰 (0.9%) 차이 — 일치 |
| Claude Sonnet (라이브) | 973 | MiniMax 대비 약 2.22배 |

- 비율 MiniMax ÷ Claude ≈ 0.45. 출력은 양쪽 모두 3토큰, 사고 토큰 0, 답은 동일했다.
- 해석: 토크나이저 수준에서 Claude가 MiniMax의 1/5로 적게 센다는 가설은 성립하지
  않으며 방향이 반대다. 단, 표본은 한국어 문장 1종 · 각 1회이고 Claude 쪽은 두
  실행 사이 캐시 생성/읽기 분할이 변동해 추정치에 불확실성이 있다. 그 변동분을
  전부 오차로 쳐도 결론(1/5가 아님)은 바뀌지 않는다.

## 2. 실측 B — 동일 작업의 양쪽 엔진 재현

### 방법

- 이 레포에서 스케줄러가 실제로 처리해 머지까지 끝난 작업 2건을 골라, 각 작업을
  동일한 프롬프트(출력 언어 지정 + 이슈 1건 + 작업 명세)와 동일한 시작 커밋의
  레포 복사본에서 양쪽 엔진으로 각 1회 재현했다.
  - 작업 A: 외부 리소스 링크 4건 검증 · 등록 (정답: PR #458)
  - 작업 B: 설계 문서의 엔진 선택 규약 문장 정정 (정답: PR #469)
- 커밋 · 푸시 · PR 생성 · 이슈 게시는 측정 환경에 없으므로 양쪽 동일하게 제외했다.
  작업 트리 변경과 결과 요약까지를 작업 범위로 했다.
- 토큰은 세션 결과 JSON의 usage와 transcript JSONL을 message id 중복 제거로
  합산한 값(집계 방식은 `scripts/gissue/lib/token-usage.ps1` 과 동일)을 대조했고,
  두 경로의 합계가 토큰 단위까지 일치함을 확인했다.

### 결과

작업 A (탐색 · 검증 · 편집):

| 항목 | Claude Sonnet | MiniMax M3 | 배율 (M3 ÷ Sonnet) |
|---|---:|---:|---:|
| 신규 입력 | 14 | 87,369 | — |
| 캐시 생성 | 42,090 | 0 | — |
| 캐시 읽기 | 276,223 | 1,479,760 | 5.36 |
| 출력 (사고 포함) | 4,399 (사고 426) | 16,807 (사고 8,914) | 3.82 |
| **총 토큰** | **322,726** | **1,583,936** | **4.91** |
| API 호출 수 | 7 | 31 | 4.43 |
| 소요 시간 | 74초 | 271초 | 3.66 |

작업 B (읽기 · 문장 정정):

| 항목 | Claude Sonnet | MiniMax M3 | 배율 (M3 ÷ Sonnet) |
|---|---:|---:|---:|
| 신규 입력 | 8 | 45,258 | — |
| 캐시 생성 | 24,226 | 0 | — |
| 캐시 읽기 | 106,368 | 330,344 | 3.11 |
| 출력 (사고 포함) | 1,368 (사고 0) | 5,049 (사고 3,071) | 3.69 |
| **총 토큰** | **131,970** | **380,651** | **2.88** |
| API 호출 수 | 4 | 11 | 2.75 |
| 소요 시간 | 24초 | 59초 | 2.46 |

합산: Claude 454,696 vs MiniMax 1,964,587 — 약 **4.32배**. 호출 합계 11회 vs 42회.

### 품질 대조

- 4건 모두 실제로 머지된 정답과 같은 결론에 도달했다 (작업 A: 신규 3건 등록 ·
  기존 등록 1건 제외 판정까지 일치. 작업 B: 규약 문장 1건의 정정 범위 일치).
- 산출 diff의 규모도 정답과 같았다 (작업 A 32줄, 작업 B 25줄 — diff 파일 줄 수 기준).

### 해석

- 호출 1회당 캐시 재읽기는 양쪽이 비슷하다 (작업 A: 회당 약 39.5K vs 47.7K,
  작업 B: 약 26.6K vs 30.0K). 총량 차이는 호출당 단가가 아니라 **호출 횟수**가
  만든다. MiniMax는 같은 일을 끝내는 데 단계를 2.8~4.4배 더 밟았고, 그때마다
  누적 컨텍스트 전체가 캐시 읽기로 다시 계수됐다.
- 사고 토큰도 MiniMax가 많다 (작업 A 8,914 vs 426). Flash는 사고를 끌 수 없고
  effort 기본값이 max이므로, effort 고정은 실재하는 절감 지렛대다.
- 출력이 장황하면 그 출력이 다음 호출들의 컨텍스트로 재읽혀 총량을 키운다.
  작업 A에서 MiniMax의 출력은 Claude의 3.8배였다.
- 한계: 표본은 작업 2건 · 각 1회이며 배율은 작업 성격에 따라 흔들린다
  (탐색이 많은 작업일수록 커진다). 샌드박스 측정이므로 절대값은 실제 스케줄러
  1회차(다건 처리 + 게시 단계 포함)와 다르다. 양쪽에 동일 조건을 적용했으므로
  비율 비교는 유효하다.

## 3. 실측 C — 운영 트래픽의 구성

- 측정 환경의 MiniMax 하네스 transcript 집계 (2026-11-09~12):
  11/09 587회 호출 96.8M 토큰, 11/10 1,186회 186.3M, 11/11 897회 136.7M,
  11/12 547회 90.4M. 호출당 평균 약 157K 토큰, 그중 캐시 읽기가 약 97~98%.
- MiniMax 콘솔 실측 (2026-11-16, 사용자 화면): 선택 구간 사용량 19.00B 토큰,
  일평균 633.43M, 캐시 적중률 96.9%. 모델 구성은 MiniMax-M3 (512k)가 지배적이고
  M3.1-Flash는 미미했다 — 스케줄러가 의도와 달리 M3로 돌고 있었다는 뜻이다.
- 사용자 보고 기준 스케줄러 트래픽은 일 약 1.5B 토큰으로, 주간 쿼터 약 5B를
  약 3.3일 만에 소진하는 속도다.
- 해석: 총량 = Σ(호출마다 누적 컨텍스트 재읽기) 다. 신규 입력 자체는 작으며,
  "뻥튀기"의 증거는 없다 — 토크나이저는 정상이고, 쿼터도 같은 방식(캐시 읽기
  포함 액면 합산)으로 차감되는 것으로 보인다.

## 4. 절감 지렛대 (실측 근거 순)

1. **호출 횟수 절감** — 스크립트로 판정 가능한 단계를 엔진 없이 처리하고
   (본체 비AI 원칙), 판단이 필요한 항목만 델타 패키지로 게이트에 보낸다.
   호출당 입력 상한과 구조화 출력으로 재호출을 막는다. (실측 B · C)
2. **effort 고정** — Flash/M3 모두 reasoning effort를 medium으로 고정한다.
   미지정 (기본 max) 으로 두지 않는다. (실측 B의 사고 토큰 차이)
3. **기본 모델 Flash** — MiniMax 전반의 기본은 M3.1-Flash, 코드 작업과 민감한
   내용은 M3, 최상위 판단만 Claude. 종량 단가도 Flash가 M3의 절반이다. (실측 C)
4. **출력 규율** — 중간 상태 나열만으로 끝내지 않고, 결과 요약은 짧게.
   출력은 다음 호출의 입력으로 재읽힌다. (실측 B)
5. **지속 계측** — 모든 엔진 호출의 usage를 `scheduler_token_usage` 레코드로
   남겨, 라우팅 변경의 효과를 실측으로 판정한다. (설계 문서 참조)

## 5. 재현 경로

- 토크나이저: 공개 토크나이저 로컬 계수 + `claude -p --output-format json`의
  1배본/4배본 차분.
- 작업 재현: 동일 프롬프트 · 동일 시작 커밋의 샌드박스 복사본에서 엔진별 1회
  실행 후, 결과 JSON usage와 transcript JSONL 합산의 이중 대조.
- 측정 원본(프롬프트, 결과 JSON, 산출 diff)은 측정 실행 환경에 보관한다.
  이 문서에는 수치와 방법만 남긴다.
