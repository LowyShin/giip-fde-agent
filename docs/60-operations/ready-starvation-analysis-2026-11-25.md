## 2. 원인 (코드 실측)

### ① 큐 순서와 READY 60분 게이트 (구 구조)
큐 우선순위가 STALE(0) → PENDING(1) → READY(2) → REVIEW(3)였고, READY는 마지막 활동 후 60분이 지나야 진입했다. 앞 그룹이 예산을 먹으면 READY는 순서가 오지 않았다.
→ **대응 완료**: PR #562 — READY를 최우선(qprio 0)으로, 60분 게이트 삭제. (Lowy님 지시 2026-11-25: "Ready인거는 시간 보지 않고 바로처리")

### ② 경과 판정의 시계가 "최신 코멘트 시각"
경과 시간(elapsed)은 상태가 바뀐 시각이 아니라 **가장 최근 코멘트 시각**으로 잰다 (KNOW-042). watchdog 코멘트(7일 579건)와 재검증 코멘트가 같은 이슈에 반복해서 달리면, 그때마다 READY의 대기 시계가 리셋됐다. 게이트가 있던 동안은 진입 자체가 계속 밀렸고, 게이트를 없앤 뒤에도 그룹 내 정렬(오래 기다린 순)이 왜곡된다.
→ **남은 과제**: 경과 기준을 상태 전이 시각으로 바꾸는 것. 단 [USER-REQUEST] 판정·신생 이슈 우선 규칙과 얽혀 있어 별도 검토로 남긴다.

### ③ Phase 1 사전 정비(고아 워크트리 정리)에 시간 상한이 없었다
`run-gissue-claude.ps1`은 CSN 잡을 시작하기 **전에** `Remove-GissueOrphanWorktrees`를 동기로 호출한다. 여기에 시간 상한이 없어, 레포 루트 직계 스캔(서브프로세스 무제한 대기)과 삭제 루프가 길어지면 이슈 처리가 시작도 하기 전에 회차 예산이 먹혔다. 머지 판정용 `gh pr list` 조회 실패가 겹치면 더 길어졌다.
→ **대응 완료 (이 PR)**: 120초 시간 예산을 넣었다. 스캔은 남은 예산으로 Wait-Job 타임아웃을 걸고, 초과분은 삭제하지 않고 "다음 회차로 이월" 로그를 남기고 넘어간다.

### ④ 후처리 정리 단계의 무제한 실행
회차 종료 시 워크트리 정리(`Invoke-GissueWorktreeCleanup`)도 같은 문제였다.
→ **대응 완료**: PR #560 (2026-11-25 머지) — 정리 단계 타임박스 + stall 마커를 다음 회차 기록에 표면화. lowyworkenv 운영본(CSN 33)에는 PR #1563으로 이식됐다. CSN 33 운영본은 이 문제로 종료 기록 없이 죽은 회차가 51회 연속 이어진 전례가 있다 (giip #4902).

### ⑤ 회차 구조: 직렬 처리 + 105분 예산 + CSN 락
이슈 1건 = 세션 1개 직렬 처리라, 앞 이슈 하나가 길어지면 뒤가 전부 밀린다. 예산이 소진되면 [BUDGET] 스킵 코멘트만 남고 다음 회차로 이월되는데, ①②③이 겹치면 **같은 이슈가 회차마다 반복 스킵**됐다 (14일 1,016건이 그 흔적). 전 회차가 예산을 넘겨 돌면 CSN 락 때문에 다음 틱이 통째로 스킵되는 경우도 있다.
